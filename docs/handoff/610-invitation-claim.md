# Ticket 610: invitation claim by an external identity

Entry point: [ticket 610](https://github.com/Hikyo-Org/Hikyo/issues/610).
Canonical contract: [social sign-in specification](../spec/social-signin.md) section 4 "Claim", sections 5 and 6, and section 14.4; [owning decision 582](https://github.com/Hikyo-Org/Hikyo/issues/582) as amended by [accepted resolution 589](https://github.com/Hikyo-Org/Hikyo/issues/589).

## Delivered behavior

- Purpose `claim` runs on both federated kinds through one shared core (`internal/service/claim.go`). The start takes the credential-establishment authority in the proof slot and runs `EstablishCredential`'s phase-1 checks without consuming it. A refusal (`malformed | unknown | consumed | expired | epoch-superseded | purpose`) is recorded as `auth.credential_authority_refused` by cause and answers the uniform 401 before any transaction row or round-trip. `purpose` covers an authority issued by recovery-code consumption (refused, so the recovery => password CHECK stands) and an account that already holds a credential of any kind.
- The transaction records `authority_id` and the invitee's account, bound by the browser cookie. OIDC transactions gained the `authority_id` mapping on both engines; the column and its CHECK arms already existed (00057/00058), so no migration was needed.
- The callback is one write transaction: provider guard, epoch, a lock on the invitee's principal (so concurrent claims serialize), the live authority re-check (by cause, so a losing concurrent claim records `consumed`), the precondition "no credential of any kind" (`auth.<kind>_refused {cause: purpose, purpose: claim}`), the identity uniqueness check (`identity-exists`, authority NOT consumed), the consume CAS through the kind-parameterised `ClaimFederatedAuthority` (stamps `established_credential_kind = oidc | oauth2`, never matches a recovery-issued row), the identity row, `auth.credential_established {established_credential_kind, identity_id, provider_id, kind}` and the session that identity's login would mint (OIDC assurance per the row's policy, OAuth2 single-factor; no reauth window) with `auth.<kind>_login {purpose: claim}`. A UNIQUE race on the identity insert rolls the consumption back and records `identity-exists` in a fresh transaction.
- The password path now also records `established_credential_kind: password` on `auth.credential_established`.
- WebUI: the establish page takes the authority first, keeps the password form, and offers one button per enabled OIDC or OAuth2 provider (never SAML; Microsoft hint as on login), barred until an authority is pasted and hidden after a recovery. Every refusal on the page, from either path, reads one sentence from the locked prototype: "That authority can't be used. Ask whoever invited you for a new one." The done page accepts purpose `claim`: success announces the session and lands on Account & security; a refusal shows the same sentence with the way back to `/establish`. The login page has no claim affordance. The preview found a horizontal overflow at 390 px that predated this ticket: the full-width "Lost your second factor? Recover with a code" button-link cannot wrap (removing the new provider row left the page 397 px wide; removing that link brought it to 390). The establish card's two links now use the login card's quiet `.login__links` (#567), and the page fits.

## Corrections to the OAuth2 half shipped in #609

The OAuth2 claim landed with #848 but diverged from the spec paragraph: start refusals were unaudited and the credential precheck answered `ErrBadPurpose` (a non-uniform 400); the callback collapsed every live-authority cause into `auth.oauth2_refused {purpose}` and a lost consume CAS returned an eventless 401; an identity UNIQUE race surfaced as a raw conflict; and the done page rejected `purpose=claim`, so a successful OAuth2 claim rendered an error. All four are fixed by moving OAuth2 onto the shared core.

## Contract and registry

- OpenAPI: `OidcStartRequest.purpose` gains `claim` (still an extensible enum); both start `proof` descriptions name the authority for `claim`; the OIDC start summary and description name the purpose. `EstablishCredentialRequest` already listed the `recovery` issuer, so the spec's "fixed in passing" item needed no change. `establish` on the OIDC start belongs to #611 and is not advertised here.
- Audit registry: `auth.oidc_login.purpose` gains `claim`; `auth.oidc_refused` gains cause `identity-exists` and an optional `purpose`; `auth.credential_authority_refused.cause` is now a closed enum of the six causes every emitter uses; `established_credential_kind` gains `password`. Enum pins in `internal/audit/audit_test.go`.
- Wire registry: both start routes declare `auth.credential_authority_refused`; both callbacks declare it and `auth.credential_established`.
- `ErrNoInvitationPath` had already left the Go code with #607; the two login-path comments that described the remaining invitation path now name purpose `claim`.
