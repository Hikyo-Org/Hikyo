Faster CI feedback: cache reuse and independent validation

Prepared 10 October 2026. This records the measured bottlenecks and the implementation being prepared for staged delivery. Hosted rollout and duration verification are pending. The companion HTML contains the full report and works offline.

What changed

Five jobs now reuse the existing trusted Go compilation cache: app-build, web-go, client, supply-chain-checks and compose-demo. The first two previously requested go-web-v2, a cache with no writer and no live entries. The client, supply-chain and Compose jobs compiled without a restored build cache. All five now read the existing go-test-v2 cache populated by test_core during trusted full validation on main. The delivery change moves that validation from every merge to nightly and manual runs. The supply-chain job also explicitly selects the pinned Go toolchain.

No Go cache family or writer was added. Go cache keys retain operating system, architecture, runner ABI and dependency/tool hashes. Tests continue to execute freshly with -count=1; the native package verifier gained that flag because restoring a compilation cache must not allow old test results to substitute for current execution. Go decides which compiled entries match current source and compiler inputs. GitHub's outer archive remains immutable until its key changes or it is removed. GitHub cache reference, Go build and test caching.

Linux core tests now become eligible immediately after changed-path classification. Previously they waited for both macOS and Windows scanning and custody checks, despite consuming no output from them. The final aggregate now requires scan-xplat directly, alongside test_core. Failed, cancelled, missing or unexpectedly skipped platform proof still blocks the result. Test coverage, shard counts, timeouts, runner providers and fork permissions are unchanged.

Source: workflow, required-job registry, cache regression tests, dependency regression tests, required-job fixtures.

What the measurements establish

The audit used 13 successful runs: nine PR validations with 47 jobs each and four main runs with 46 jobs each. The sample consumed 4,971.1 runner-minutes. Earlier main runs completed in 32.6 to 36.7 minutes; a saturated main run took 150.8 minutes. The latest running main was used only to confirm repeated cache misses and compilation, not included in the successful-run aggregates.

A controlled local compilation probe used a fresh temporary Go build cache followed by the same warm cache. go test -count=1 -run '^$' ./internal/isolation took 56.599 seconds cold and 11.323 seconds warm on macOS arm64 with Go 1.27.2 and an already populated module cache. Both commands passed. No test cases were selected: this isolates compilation and test-binary startup, not integration-test performance. It demonstrates reuse locally, not the expected hosted speedup.

The removed platform dependency delayed Linux job creation by 5.15 to 67.15 minutes across the sample, including time that the platform jobs spent waiting for runners. Those are eligibility delays, not promised savings. Jobs can still queue after becoming eligible, and another required job may remain on the critical path. Similarly, pre-test overhead includes downloads, linking and process startup; it is not all removable compilation.

What still limits development speed

Runner contention remains the largest source of the multi-hour cases. The earlier polling-gate investigation and repair identified six waiting gates consuming over nine runner-hours. Its local replacement is still configured for hosted observation as ci-required-next; activation remains pending. The speed changes here do not activate that replacement or remove the existing required gate.

Race tests consumed 45.3% of sampled runner execution, browser tests 17.9%, and isolation tests 9.3%. One long race step spent roughly 90% of its duration inside reported package tests. Cache improvements cannot eliminate that test work. The sample also includes final aggregate jobs waiting another six to twelve minutes for a runner before executing for around ten seconds. No claim of a ten-minute full CI run is supported by the current measurements.

The cache API confirmed occupancy and a pnpm entry disappearing between runs, but did not expose the configured storage limit: that endpoint returned HTTP 402. Automatic eviction is plausible, not established. No caches were deleted remotely.

Validation and delivery

New cache regression tests failed against the original orphan/missing-reader configuration and passed after the repair. Mutation cases cover missing consumers or writer, mismatched paths and keys, missing ABI/tool inputs, PR writes, duplicate writers, invalid step ordering and replayed test results. Required-job fixtures cover failed, cancelled, skipped and missing platform results even when Linux tests pass.

The transition also supports PRs whose base still has the old indirect gate registry. The aggregate recognizes only that exact legacy shape, checks the real platform result against the boolean test plan, then removes only the extra platform key before invoking the base-controlled checker. It never manufactures success or changes the Linux result. Current and unknown registry shapes are not rewritten. Forty-eight executable shell scenarios test old, new and unexpected policies, and demonstrate that a permissive checker in the PR checkout cannot replace base policy.

Local Go tests, Go vet, Actionlint, ShellCheck, required-job, cache-policy, artifact-reuse, changed-path and trusted-script fixtures passed. Independent adversarial review found no actionable issues in the cache or migration changes. Hosted duration improvement remains unmeasured; it requires a comparable post-delivery run with actual cache-hit and queue evidence. The speed changes and observer are delivered together; replacing the required polling gate follows hosted proof.

The implementation was aligned with d3bf670c4, preserving PR #881's Storybook checks. The linked GitHub runs provide the source for hosted measurements; raw snapshots and the local compilation probe were retained as investigation evidence.

Main and release validation after rollout

Merging a PR no longer triggers ci.yml again. The required PR graph, strict up-to-date branch policy, signatures and resolved-review requirements remain in force. Other independent consumers, including Pages and CodeQL, retain their existing triggers.

The nightly workflow calls the complete read-only CI graph for its own github.sha; its protected publication job cannot start unless that graph succeeds. This also seeds the existing trusted caches. A manual main run provides full validation and development snapshot artifacts when needed. Its classifier, planner, race scheduler and aggregate refuse non-main dispatches; its full-plan requirement does not accept selective PR validation.

For stable release preparation, from a checkout with authenticated gh access:

gh workflow run ci-main.yml --repo Hikyo-Org/Hikyo --ref main
gh run list --repo Hikyo-Org/Hikyo --workflow ci-main.yml --event workflow_dispatch --limit 5

The dispatch requests validation of main at the time GitHub accepts it. Wait for that run to complete successfully and use its exact source commit for release preparation. The existing release ceremony checks the exact commit and fails closed if its full main validation is missing, unfinished or failed. A historical successful push run remains acceptable for compatibility; a PR validation or unrelated workflow cannot substitute. These commands prepare validation only and do not publish a release.

The new main-context tests execute the workflow shell for manual, scheduled and repository-dispatched validation, prove full-plan selection, and reject feature refs, failed jobs and a job/result set consistent with a selective docs-only plan. Nightly fixtures reject every publication result except success. Fuzz reporting retains issue creation for failed trusted manual/nightly runs; 32 source-context cases cover workflow identity, path, event, branch and conclusion. Full CI-package tests, controller tests and race tests, Go vet, all changed workflow linting, cache/artifact/trusted-script/nightly/release shell fixtures and whitespace checks passed before the initial PR. Independent review identified the fuzz-report dependency and it was repaired in this change.

First hosted review corrections

PR #882's CodeQL scan flagged PR-head checkouts in a reusable graph that also serves manual and nightly callers. Event-specific checkout guards did not resolve the analyzer's cross-caller warning. The graph now accepts a required immutable revision from its caller and verifies its binding to the authenticated GitHub event before every checkout, including the final aggregate. The PR caller supplies its exact head; main and merge-group callers supply github.sha. An input-free ci-main.yml wrapper owns manual main validation. There is still one validation graph, with no alert suppression or cache-policy exception. The 30267d0c2 scan cleared the broad checkout findings but reported ten artifact-consumer alerts and one remaining floor-benchmark checkout alert. The artifact query propagated pull_request_target from the mixed PR/merge-group controller despite the job-level event guard. Merge-group validation now has a separate ci-merge-group.yml entrypoint; the PR-target controller only verifies PR-scoped validation and has no call path to the validation graph. The floor benchmark uses the same immutable revision contract, while direct tag runs retain their exact tag commit. Same-run artifact reuse is unchanged. Hosted CodeQL confirmation remains pending on this follow-up.

The initial hosted run also exposed a duplicate ARM floor benchmark when its own workflow changes. The obsolete standalone PR trigger was removed; the full changed-path plan and required aggregate still enforce the reusable benchmark. Tag triggers remain unchanged. The observer now uses GitHub's supported queue: max setting to retain up to 100 pending publisher runs, with periodic repair retained for overflow or missing events. Race, web and API follow-up

The next pass separates actual test execution from compilation and queue delays. In successful run 38063556913, the slowest race shard spent 74 minutes 48 seconds queued and 19 minutes 18 seconds executing. Its race cache hit restored in about five seconds, and tests began about four seconds after the scheduler started. More compilation caching cannot remove that shard's 18-minute race-test step. The API package itself took 2.385 seconds normally and 13.211 seconds under the race detector.

Browser groups are rebalanced using per-test timings, with the same twelve spec files, four groups, desktop/mobile viewports, single worker, zero retries and flow-closure gate. Bounded experiments

A real PostgreSQL experiment compared disk and capped tmpfs in ABBA order, with the same precompiled race-test binary and all fourteen origin-recovery PostgreSQL cases. Median wall time was 13.365 seconds on disk and 12.869 seconds on tmpfs, a 3.7 percent local difference. fsync, full_page_writes and synchronous_commit remained enabled, and a committed row survived immediate PostgreSQL process stop/restart in every round. This macOS/Docker result does not establish a worthwhile hosted speedup, so no RAM-storage change is shipped.

An attempted SQLite optimization reused existing schema-only preparation for the origin-recovery feature test. Two precompiled race processes per version reduced the fourteen-case target median from 96.559 to 17.798 seconds (81.6 percent), using -test.count=1, -test.parallel=4 and GOMAXPROCS=4 on macOS arm64. Compilation was excluded.

This optimization was rejected and reverted. A new authority-independence regression correctly failed: schema-only migration had already created an installation ID and recovery incarnation, and subsequent boots resumed the copied identity. Fresh encryption roots did not make those identities independent. Running the same oracle against fresh fixtures passed, confirming the shortcut caused the failure. All twenty-eight candidate SQLite/PostgreSQL origin cases passed, but that was insufficient proof of fixture isolation. No service-test changes remain in the PR, and the 81.6 percent result is not a shipped improvement.

The profile identifies repeated SQLite migration setup as a concrete future optimization target. A safe improvement must preserve fresh installation authority and genuine boot admission. PostgreSQL RAM storage and fixture identity changes are excluded from this delivery.
