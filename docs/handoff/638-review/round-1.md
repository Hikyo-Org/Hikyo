R1: 5 blocking objections. Do not lock [issue #638](https://github.com/Hikyo-Org/Hikyo/issues/638) yet.

1. **CRITICAL: existing updater violates the proposed rollback boundary.** Proposal says platform apply stays disabled and automatic rollback stops at `schema-write-started` (proposal:17 (historical `docs/research/signed-upgrade-compatibility.md:17`, file no longer present), proposal:121 (historical `docs/research/signed-upgrade-compatibility.md:121`, file no longer present)). Current docs enable remote apply ([upgrades.mdx:57](../../site/src/content/docs/docs/upgrades.mdx) (historical line 57)); API submits jobs ([updates.go:147](../../../internal/service/updates.go) (historical line 147)); executor automatically rolls back after any apply or health failure ([updater.go:259](../../../internal/updater/updater.go) (historical line 259)); Compose restores the database unconditionally ([hikyo-update-compose:29](../../../install/updater/hikyo-update-compose) (historical line 29)). Helper restart merely marks the job failed ([updater.go:391](../../../internal/updater/updater.go) (historical line 391)). Fix: explicitly classify current updater as unsafe legacy and hard-disable apply before amendments become operative. Replacement must consult durable DB phase state, resume only the exact target/generation, rollback only from proven `prepared`, and leave `schema-write-started` in maintenance plus `restore-required`.

2. **HIGH: pending state does not structurally fence HA writers.** Proposal requires generation checks but never defines how maintenance activation waits for already-open transactions or permanently rejects a partitioned old process (proposal:68 (historical `docs/research/signed-upgrade-compatibility.md:68`, file no longer present), proposal:97 (historical `docs/research/signed-upgrade-compatibility.md:97`, file no longer present)). Current transaction boundary has no upgrade-generation fence ([tx.go:62](../../../internal/store/tx/tx.go) (historical line 62)); PostgreSQL advisory locking covers migrators only ([migrate.go:201](../../../internal/store/migrate/migrate.go) (historical line 201)); HA nodes provide heartbeat observation, not exclusion ([ha.go:152](../../../internal/app/ha.go) (historical line 152)). Fix: every domain transaction must lock/read one upgrade-control row and compare process-admitted release plus generation. Maintenance activation increments generation under an exclusive row lock, thereby waiting for earlier transactions. Clearing maintenance must not re-admit stale processes. Add crash tests after every phase and migration commit, plus partitioned-old-writer commit tests.

3. **HIGH: backup requirement contradicts locked behavior and demands proof the helper cannot obtain.** Proposal requires a verified, readable backup while denying recovery private keys to the helper (proposal:114 (historical `docs/research/signed-upgrade-compatibility.md:114`, file no longer present)). Locked ops and current implementation permit migration with a loud no-recipient skip ([ops-spec.md:193](../../adr/ops-spec.md) (historical line 193), premigration.go:57 (historical `internal/app/premigration.go:57`, file no longer present)). Current backup manifest contains only engine, schema version and time, not instance, release, migration digest, restore epoch or generation ([backup.go:61](../../../internal/store/backup.go) (historical line 61)). Fix: explicitly supersede loud-skip success for populated-database upgrades. Define an externally verifiable receipt containing backup ID, ciphertext digest, instance ID, source release/schema/migration identity, restore epoch, generation and recipient fingerprints. Bind a fresh operator-signed drill attestation to that receipt; helper verifies public proof without receiving age or root private keys.

4. **HIGH: nightly and compromised-key recovery trust remains undefined.** “Keyless profile” names OIDC claims but omits pinned Fulcio/Rekor roots, inclusion proof/checkpoint, trusted-time rules, offline verification and exact artifact binding (proposal:49 (historical `docs/research/signed-upgrade-compatibility.md:49`, file no longer present)). Current nightlies are explicitly unsigned ([nightly.yml:179](../../../.github/workflows/nightly.yml) (historical line 179)). “Operator-held recovery proof” has no schema, issuer, verifier, replay binding or custody model. Worse, current revocation rules reject every release signed by a revoked primary ([mvp-boundary.md:98](../../adr/mvp-boundary.md) (historical line 98)), while proposal refuses revoked bridge nodes, potentially trapping an installed source during emergency recovery. Fix: define `nightly/v1` signed bundles completely, then define a recovery-root-signed, one-use bridge statement bound to exact source, target, instance, restore epoch and generation. Cover nightly-to-stable and revoked-stable-source recovery explicitly.

5. **HIGH: Flux Git credential blast radius is not closed.** Proposal claims credentials can update one branch/path and makes repository isolation conditional (proposal:141 (historical `docs/research/signed-upgrade-compatibility.md:141`, file no longer present)). Ordinary Git credentials are repository/ref scoped, not path scoped. Current adapter uses ambient credentials and pushes `HEAD` directly ([hikyo-update-flux:18](../../../install/updater/hikyo-update-flux) (historical line 18), [hikyo-update-flux:30](../../../install/updater/hikyo-update-flux) (historical line 30)); compromise can commit arbitrary Flux-applied objects. Fix: require a dedicated single-application repository unless a tested server-side pre-receive policy restricts the exact diff. Also require non-force/non-tag credentials, protected ref, namespace-scoped Flux service account, fixed object-kind/name admission and signed-image enforcement. Explicitly retire current host-helper Flux backend because the decision selects a separate controller.
