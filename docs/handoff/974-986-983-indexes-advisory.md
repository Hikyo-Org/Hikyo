## Changes and invariants

Migration `00077_authorization_pending_indexes.sql` adds, on both engines:

- `grants_principal (principal_id)` for principal-scoped permanent-grant reads.
  This is a narrow index; no grant payload columns are duplicated in it.
- `pending_changes_owner_key
  (org_id, project_id, environment_id, owner_id, key_id)` for owner equality
  followed by the existing exclusive key cursor.

Historical migrations, query sources and generated query APIs are unchanged.
The original pending-change uniqueness constraint remains intact. The migration
fixture rejects duplicate owner/key rows and walks all 10 selected-owner drafts
in pages of 3, checking every expected key in order.

The source-owned development compatibility declaration was regenerated by the
repository's compatibility generator in development mode against an empty
PostgreSQL 18 scratch database. A structured comparison verified that only migration 77 and
the two resulting schema hashes changed. Historical migration entries and source
edges are identical. The legacy backup drill explicitly admits the new suffix
and removes only these data-free, non-unique indexes before catalog comparison.

The [revision model](../adr/revision-model.md),
[system architecture](../adr/system-architecture.md), and
[tenant isolation](../adr/tenant-isolation.md) remain binding. Advisory runtime
code is unchanged. Authentication and authorization still run in a fresh read
transaction per received event. Privacy, restore-epoch and temporary-grant expiry
predicates remain in the complete grant query.

Two exact test-file permissions were added to the driver-handle analyzer's
existing fixture registry: historical query-plan inspection and the isolated,
signed-admitted benchmark. Runtime importer permissions and analyzers are
unchanged.

## Query-plan evidence

The fixture starts at migration 76, seeds 1,000 principals, 10 organizations,
100 projects, 10,000 unique permanent grants, 10,000 keys and 10,000 pending
changes, then applies the new migration. Each project holds 100 keys and exactly
100 drafts: 60 for one owner, 10 for the selected owner and one for each of
30 other owners. Each organization has exactly 1,000 unique principal/org grants.
These respect the service's caps of 100 pending changes and 1,000 keys per
project, and 1,000 grants per organization. The fixture asserts the per-scope
counts so oversized single-project stress data cannot silently return. It reads the actual
complete sqlc queries, including both grant arms and all security predicates.
Statistics are refreshed on each side of the plan comparison. Plan data uses
synthetic identifiers and unset drafts without ciphertext payloads; it exercises
access paths and pagination, not payload throughput.

SQLite uses `EXPLAIN QUERY PLAN`; PostgreSQL uses
`EXPLAIN (ANALYZE, BUFFERS)`. No planner hints or disabled scan methods are used.

| Engine/query | Before migration 77 | After migration 77 |
| --- | --- | --- |
| SQLite complete grants | Permanent arm `SCAN g`; temporary arm already uses `access_grants_principal`. | Permanent arm `SEARCH g USING INDEX grants_principal (principal_id=?)`; temporary arm unchanged. |
| SQLite pending page | Existing unique index seeks scope and `key_id>?`. | `pending_changes_owner_key` seeks scope, `owner_id=?` and `key_id>?`, without a temporary sort. |
| PostgreSQL complete grants | Permanent arm sequentially scans 10,000 grants, filtering 9,990; complete query accesses 103 shared buffers. | Bitmap scan through `grants_principal`, 10 exact heap blocks; complete query accesses 21 shared buffers (19 hits and 2 reads). |
| PostgreSQL pending page | Existing unique index; 3 rows, 1 index search, 6 shared-buffer hits, no sort. | Same existing unique index; 3 rows, 1 index search, 4 shared-buffer hits, no sort. |

PostgreSQL did **not** select the new pending index on this capped workload.
The lower after buffer count on that unchanged path is not evidence of an index
benefit; these captures are not a cache-controlled latency experiment. The
migration test independently checks both new catalog definitions and exact key
order. It retains natural PostgreSQL pending plans rather than requiring a
particular optimizer choice. Exact cursor/owner/uniqueness checks still run on
both engines. PostgreSQL pending-page speedup is unproven here.

PostgreSQL can check a later equality inside an existing multicolumn index even
when it follows a range column; that does not necessarily narrow the scanned
portion. See the [PostgreSQL 18 multicolumn-index documentation](https://www.postgresql.org/docs/18/indexes-multicolumn.html).
The new order makes the owner equality part of the leading bound in both
engines; the measured SQLite plan demonstrates that change. The shared migration
shape does not imply that PostgreSQL must prefer it for a 100-draft project.

Small PostgreSQL tables may legitimately choose sequential scans. The plans
support the narrow grant index on both engines and owner selectivity on SQLite,
not a production latency claim or measured PostgreSQL pending-page improvement.
Each index adds storage and write maintenance; neither cost is quantified here.

## Advisory fan-out investigation

`BenchmarkAdvisoryFanout` measures the post-commit `published()` callback and
real per-event session resolution and authorization against disk-backed SQLite.
It excludes encryption, publish commit, HTTP/SSE serialization, connection setup,
fixture construction and external adapters. Declared keys and the initial
snapshot come from the existing production-service benchmark fixture.

The workload has 10,000 unrelated permanent grants using unique principal/org
pairs, capped at 1,000 grants per noise organization, eight session-authenticated
reader principals, and 1, 8 or 32 streams in one organization. At 32 streams,
each principal has four streams and an additional principal's subscription must
hit the organization cap. Bursts contain one summary plus 8, 64 or 300 changed-key
events. Consumers actively drain; the raw queue remains bounded at 32.

A test-only driver counts actual transactions. Every sample asserts that its
read-transaction count equals its processed/delivered event count. Dropped
streams are counted from early channel closure, not inferred from the offered
fan-out size. Reconnection and fixture setup are outside timing.

Three timed iterations per final case, Apple M2 Pro, darwin/arm64. Values
are means per burst, with event counts at Go's printed precision; they are not
latency percentiles or a capacity guarantee. Processed events and counted read
transactions are equal in every iteration.

| Streams | Changed keys | Mean ms | Offered events | Processed events = read transactions | Dropped streams |
| --- | --- | --- | --- | --- | --- |
| 1 | 8 | 1.871 | 9.000 | 9.000 | 0 |
| 1 | 64 | 6.724 | 65.00 | 32.00 | 1.000 |
| 1 | 300 | 7.988 | 301.0 | 32.33 | 1.000 |
| 8 | 8 | 15.444 | 72.00 | 72.00 | 0 |
| 8 | 64 | 38.270 | 520.0 | 264.0 | 8.000 |

| 32 | 300 | 140.160 | 9632 | 1056 | 32.00 |

The full benchmark command ran from 20:24:33 to 20:25:00 UTC on 2026-10-18,
including build/fixture overhead outside the timed loops. At both endpoints,
this task was the sole running queue job and one job was waiting. Host load
averages (1/5/15 minute) were 4.98/6.73/7.76 at start and 4.80/6.54/7.66 at
end. These endpoint observations do not prove absence of other host work or
continuous isolation. No isolated-performance claim is made.

At the capped 32-stream/300-key case, Go also reported 42,246,469 B/op and
606,940 allocs/op. Those are allocations during the measured window, not RSS
or a memory ceiling. The short bursts delivered all events; the larger bursts
dropped streams and processed far fewer events than the offered fan-out.
These samples support keeping the security contract and bounded-drop behavior;
no additional advisory runtime optimization is justified by a demonstrated
regression here. There is no before/after advisory speedup claim.

The new both-engine conformance scenario receives one event, then expires the
credential or removes the project grant before the next event. Expiry must close
the stream. Grant removal must suppress the next topology event; a later,
still-authorized environment event acts as an ordered barrier. Existing real
session revocation and per-object projection scenarios remain in the corpus.
A deterministic burst test checks the 32-event queue and empty reconnect.

These synthetic samples do not establish production throughput, PostgreSQL
advisory performance, a performance regression, or deployment-floor compliance.
The shared host experienced substantial resource contention. This task's broad
commands run sequentially through a shared queue whose operator can admit
concurrent jobs. Benchmark start/end timestamps, host load and queue overlap
observations are retained with the measured results; the samples do not
establish isolated performance. No stream authentication cache or authority batching is added.
