Default development startup

Actual zero-config CLI startup and restart now pass. The end-to-end browser setup exposed a failure before the app could start.

Cause and decision

The default database path is relative. Resolving symlinks in its parent . kept a relative custody path, which strict development-custody validation rejected.

Question: loosen custody validation or canonicalize the caller's default path? Choice: make the existing database parent absolute before resolving it. The final .hikyo-development directory keeps all nofollow, owner, type, and permission checks.

Evidence

Two focused tests passed under the race detector, zero skips, 39.810 seconds including an actual CLI build. The CLI starts from a fresh working directory with default DB/root/custody paths, reports readiness 200 and healthy development admission, and preserves its root and generation after abrupt termination and restart.

A symlink at the default custody directory remains rejected without modifying its target or creating a datastore. Source is ready for the parent to rebuild the UI test binary and resume locked-prototype verification.

Handoff: docs/handoff/663-default-development-startup.md.

Development host commands

The next CLI step exposed a separate production-only admin dispatcher. Host groups now accept exactly one leading --dev, such as hikyo admin --dev create .... Backup and restore use the same prefix. Later literal values remain untouched, and the unsupported HIKYO_DEV environment key does not change the trust domain.

Decision: require explicit selection instead of inferring trust from the database. Help, README, and getting-started instructions now match.

Focused race checks passed with zero skips: command package 2.300 seconds and actual CLI app package 19.748 seconds. The real executable refused production admin creation against the development datastore without changing its ledger, then created the administrator with the explicit flag and preserved root and generation across restart.
