F2 atomic upgrade ledger

Issue 660, governed by merged ADR at 373910cca63eb8a2e2e6b5a079cc285b64a2ae95. Implementation worktree /tmp/hikyo-upgrade-ledger. Local implementation evidence; no commit, pull-request delivery or 1.0 release is claimed here.

Implemented: both-engine atomic bootstrap, exact genesis inspection, applied/pending state machine, full identity CAS, trust floors, one-use nonce consumption, route maintenance, restore incarnation reconciliation and the same-connection migration seam. Local verification passed; independent review and delivery remain pending.

Boundary

These are storage primitives. They do not authenticate release claims, prove a backup, drain old writers or mint runtime permission. F1 verifies release/route trust, F4 verifies operator evidence, F3 provides transaction fencing and F5 invokes the mandatory startup/migrate/restore gate. Existing pre-gate binaries and direct datastore administrators are not retroactively fenced.

Decisions and reasons

QuestionOptions consideredRecommended choice
Which legacy databases?Infer previous version; accept historical schema families; pin one documented exact source.Pin governance commit 373910cc, schema 44, with full engine-specific catalog and 43 exact migration byte hashes. Fresh installation is separate genesis. Unknown history refuses.
How does ledger installation become safe before goose?Ordinary migration; control-only preparation; atomic bootstrap under the existing engine lock.Inspect first, then create control, pending and nonce tables plus complete pending operation in one transaction. Never call goose to inspect absent state.
How can a legacy backup bind an incarnation before a ledger exists?Pretend a live state exists; install authority before verifying backup; explicit proposed bootstrap identity.The operator generates a proposed random incarnation. F4 verifies its backup and attestation against actual pre-ledger instance, epoch, full schema and migration bytes. F5 rechecks under exclusion; F2 atomically installs that proposal with pending state and nonce consumption. Proposal is never reported as live state.
How is restored authority invalidated?Only archived counter+1; external distributed counter; random recovery incarnation plus existing strongest credential epoch.Use a fresh 32-byte CSPRNG incarnation inside the existing restore transaction and preserve the resolver's strongest epoch advancement. Keep archived pending evidence invalidated/restore-required. Repeated archive restores get distinct authority domains.
How are trust and one-use proof claims stored?Optional callback/context data; separate writes; closed typed acceptance in pending creation.Persist release-root digest, authenticated metadata/catalog/highest-release floors and nonce consumption atomically. Key nonce uniqueness by domain, instance, incarnation, epoch and nonce. F1/F4 verify claims; F2 never treats structure as signature authority.
What happens at a healthy intermediate hop?Clear maintenance; retain maintenance across the complete route.Bind route origin/digest/length/hop. Intermediate healthy advances applied identity but retains maintenance and generation; next hop preserves the route. Only the final healthy hop clears maintenance.
How do release builds and boot compare schema?Maximum migration number; independently invented digests; one shared catalog algorithm.Shared SQLite/PostgreSQL catalog APIs hash versioned canonical inventory and exact goose history. Only separately validated exact gate-owned objects are omitted. Changed control objects and arbitrary upgrade-prefixed objects refuse.
How should SQLite aliases be handled?Path normalization only; retained file identity plus single-link requirement.Resolve canonical path, require regular single-linked file and recheck retained identity under the migration lock. F3 supplies runtime lifetime exclusion; this package does not claim it already exists.
How does candidate migration keep PostgreSQL lock ownership?Second pooled connection; fork goose; maintained one-use driver lease.Use the caller-owned connection inside sql.Conn.Raw with immutable embedded SQL. The real reentrant goose locker releases only its own acquisition. The lease cannot reconnect, and cancellation preserves the durable post-write marker.
How does restore obtain control schema?Commit a preparation database; overwrite existing state; create exact empty tables in the import transaction.The restore primitive validates authenticated source schema/manifest before creating exact empty control tables. Existing tables must be exact and empty. F5 places this before inventory/import within the same transaction, then advances existing credential epochs and rotates incarnation before commit/publication.
How should archive tests coexist with runtime store importing upgrade?Omit tests; duplicate production embeddings; separate external archive integration from internal primitive fixtures.Keep every archive regression in external upgrade_test. Internal fixtures use unchanged repository SQL through maintained goose in owned test databases. Production immutable embeddings remain unchanged. The exact external recovery harness receives only its existing callback driver access.

Validation

Latest ordinary ledger run: 129 cases passed with real SQLite and PostgreSQL 18.6, zero skips. Relevant existing storage, migrations, transaction, crypto and architecture checks: 368 cases passed, zero skips. Go vet passed. The complete 129-case ledger race run passed in 90.512 seconds. Three subsequent focused race cases verify the public approved-legacy schema accessor against actual engine catalogs. Windows amd64 cross-compilation passed (compile only). Results are recorded in validation.json.

Meaningful failure cases cover unknown/changed schema and migration bytes, partial control state, stale instance/domain/epoch/incarnation/generation/target, illegal phase transitions, same-target restart, downgrade, nonce replay, expired/future evidence, trust rollback/equivocation, concurrent migrators, abrupt child-process exit before/after bootstrap commit, post-write commit ambiguity, SQL cancellation and PostgreSQL backend termination. Real archive imports prove repeated restores produce different incarnations and failed SQLite recovery mutation leaves no published destination. Tests use isolated owned databases; credentials are never included in reports.

Independent review fixes: 18 both-engine race cases passed. Actual instance-row identity and restore fences are checked before source proof/export, while normal credential-only revocation remains valid. Fresh identity reconciliation is limited to the first schema-applied hop and refuses populated domain state. Read-only control inspection permits post-write domain drift for recovery decisions; separate healthy key inspection preserves reader lifetime and phase bounds.

Pinned genesis provenance

Both declarations come from applying unchanged embedded migrations at the exact governance source commit. SQLite inventory contains 143 structural objects; PostgreSQL contains 3134 catalog records. Each binds 43 ordered SQL files with maximum version 44. The records represent engine-specific definitions, including SQLite implicit constraints in CREATE statements and PostgreSQL explicit constraints/index/catalog records. Owner/grant names, physical OIDs, sequence current values and optimizer statistics are outside schema identity; installation custody and runtime data retain their existing responsibilities. Full migration manifests and schema inventories are committed under internal/store/upgrade/genesis.

Artifact and copied F1 dependency hashes. The shared releaseidentity leaf is F1-owned; shape validation is not signature verification. The canonical catalog APIs are reused by release generation, snapshots and boot rather than duplicating fingerprints.

Remaining integration

F5 must reconcile fresh bootstrap identity with migration 20's generated singleton, verify actual source/target catalogs and bounded candidate health, map actual verified F1/F4 results, and call restore schema/epoch/incarnation primitives inside the actual import transaction. No unrestricted runtime constructor is introduced here. Runtime F3 fencing, final combined application checks and release delivery remain separate required work.
