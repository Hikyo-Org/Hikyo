PostgreSQL UTC timestamp correction

5 September 2026. The frozen generated-client acceptance harness found that PostgreSQL-backed whoami returned offset-bearing session timestamps. Its unchanged Zod datetime validators rejected these responses. SQLite returned canonical UTC timestamps.

Cause and correction

The store contract already requires UTC timestamps. In the pinned pgx v5.10.0 implementation, binary timestamptz decoding uses Go's local timezone unless a scan location is configured; text decoding preserves the PostgreSQL session's offset. Setting the database session timezone alone does not correct binary decoding.

Every new store pool connection now registers pgx's supported TimestamptzCodec{ScanLocation: time.UTC}. Timestamp arrays receive the same element codec because pgx's default array codec retains its own element-type pointer. This changes the returned location and JSON representation while preserving the stored instant and microsecond precision. Generated query wrappers, direct scans and nullable values use the same boundary.

Evidence

The real PostgreSQL regression runs in a subprocess with TZ=Pacific/Auckland, while two simultaneously held physical database connections use Asia/Kathmandu. Binary and simple-text queries cover winter and summer timestamps, positive and negative input offsets, date crossings, time.Time, generated pgtype.Timestamptz wrappers, arrays and nulls. Every decoded value must preserve the exact instant, use UTC and serialize with Z.

Before the fix, all eight connection/protocol/input cases failed UTC/JSON assertions. After the fix, the regression passed. Full store and race validation results are recorded in the accompanying handoff. The test uses a uniquely created scratch database and leaves existing databases unchanged.

No schema migration, HTTP timestamp rewriting or validator change is involved. Parent delivery owns the combined frozen-client acceptance, review, CI and merge; this report does not claim those gates completed.
