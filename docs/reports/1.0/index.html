## Problem Statement

Self-hosting developers and platform engineers who want to manage secrets and configuration across environments face a market where every surveyed product either paywalls the operational core - audit, RBAC, SSO, SCIM, secret scanning, the classic `/ee` lineup - or lacks the combination of explicit multi-environment values, schema validation, and fully-open licensing entirely ([competitive-landscape](https://github.com/Hikyo-Org/Hikyo/blob/main/docs/research/competitive-landscape.md)). They end up with hand-maintained `.env` files that drift, no validation before a bad value reaches production, no answer to "who saw this secret and when", and no trustworthy self-hosted home for production secrets that works from a phone in the server closet as well as a desk.

## Solution

Build **Hikyo 1.0**: a fully open-source (MPL-2.0, published no-`/ee` pledge), self-hosted control plane for validated secrets and configuration across environments - Docker Compose and Kubernetes first-class, single multicall Go binary with embedded SPA, sqlite and postgres, Raspberry Pi 4 as the calibration floor.

> Fully open-source secrets & config across environments - with validation, explicit per-environment values, and no enterprise tier.

The **environment matrix** is the signature surface: every key × environment at a glance, every value explicitly `set` or `absent` (no inheritance, no fallback), schema-validated before publish, secrets revealed only through an audited ceremony. Delivery is a gradient: *if your job can fetch, federate; push what must exist before the first fetch.* Four classic paywall items ship free in 1.0 as wedge proof: GitHub Actions adapter, SAML SP, SCIM provisioning, secret scanning.

The corpus is the spec; this build implements it. Scope, acceptance criteria, and sequencing: [mvp-boundary](https://github.com/Hikyo-Org/Hikyo/blob/main/docs/adr/mvp-boundary.md).

## User Stories

Core domain

1. As a self-hosting developer, I want Hikyo as a single multicall binary with an embedded web UI running on sqlite, so that I can run it on a Pi-class box with no external dependencies.
2. As a self-hosting developer, I want secrets and config organized as Instance → Organization → Project → Environment → Folder → Key/Value, so that every value has exactly one explicit home.
3. As a self-hosting developer, I want each key declared once per project with a `secret | config` classification, so that a matrix row is uniformly secret or config and typing an undeclared name is a key creation, never a silent value write.
4. As a self-hosting developer, I want every `(key, environment)` value to be explicitly `set` or `absent` with no inheritance or fallback source, so that what delivers to an environment is exactly what the matrix shows.
5. As a self-hosting developer, I want the environment matrix to surface gaps, validation problems, and required-but-absent keys at a glance (never color-only), so that I spot drift without reading docs.
6. As a self-hosting developer, I want schema validation - six types + `any_of`, whole-value RE2 patterns, JSON Schema subset on `json` keys, presence rules, `forbidden_in`, key groups - enforced at publish, so that invalid configuration never reaches a workload.
7. As a self-hosting developer, I want per-user pending changes and selective publish with key-group auto-close, so that edits stage privately and land atomically per project.
8. As a self-hosting developer, I want per-environment revision history with diff and restore-as-normal-publish, so that rolling back a bad publish is safe, validated, and least-blast.
9. As a self-hosting developer, I want pins on non-current snapshots as quota-bounded resources with mandatory expiry, so that a workload can hold a known-good revision without blocking GC forever.
10. As an org admin, I want payload retention with an org default and project cap, permanent lineage, and loud failures on collected-revision fetches, so that storage stays bounded without silent data loss.

Disclosure & editing

11. As a self-hosting developer, I want revealing a secret to be a ceremony - purpose-bound re-auth (passkey/TOTP), sliding window, auto-remask, one audit event per key including clipboard copy - so that disclosure is always deliberate and attributable.
12. As a self-hosting developer, I want write-only editing without reveal, so that I can rotate a secret I am not entitled to read.
13. As a self-hosting developer, I want copy-to, bulk-apply, and clone-at-creation as explicit one-time operations under the locked permission formulas, so that shared values are ergonomic without any ongoing inheritance relationship.
14. As a self-hosting developer, I want secret scanning at value entry backed by a normative ruleset, so that pasted foreign credentials are caught at save, not after a leak.

AuthN, AuthZ, audit

15. As a human user, I want local accounts (Argon2id) plus multi-provider OIDC, WebAuthn, TOTP, and single-use recovery codes, so that login matches my infrastructure and the local floor is never disableable.
16. As an org admin, I want `(principal, capability, scope)` grants issued through eight role templates expanding at grant time, so that access is predictable and revocation is immediate.
17. As an org admin, I want protected environments where effective reveal windows drop to zero and publish-into-protected takes a ceremony, so that production is stricter than dev.
18. As an org admin, I want unauthorized resources to be uniformly nonexistent - content and counts - so that nothing leaks across tenant boundaries.
19. As an org admin, I want SAML (SP) sign-in and SCIM provisioning free in core, so that IdP-driven membership needs no enterprise tier.
20. As an operator, I want an on-host break-glass path with local authority only, so that an IdP outage or lost grant never locks the instance permanently.
21. As an auditor, I want two append-only trails with a closed `category.action` registry, denials durable before response, per-key disclosure events, and re-authorized paged export, so that every access question is answerable.

Crypto & operations

22. As an operator, I want envelope encryption (root → master → project DEKs, XChaCha20-Poly1305, per-kind AAD) with five rotation operations including crash-safe root rotation, so that key hygiene never requires downtime or a re-import.
23. As an operator, I want the headline guarantee held: a stolen database plus backups without the root key yields no values and no replayable credentials.
24. As an operator, I want age-encrypted backups with mandatory root-key escrow, and a restore that kills bearer credentials, re-validates identity links, and stages grants for per-principal reconciliation, so that restore never resurrects stolen access.
25. As an operator, I want goose migrations with fail-closed serving and a tested upgrade path with pre-migration export, so that upgrades are boring.
26. As an operator, I want doctor, static-series metrics, every ops bound to fail as a named refusal, and zero unsolicited egress, so that the instance is diagnosable and air-gap-safe.

Surfaces

27. As a developer, I want a spec-first `/api/v1` (OpenAPI 3.0.3) with additive-only post-freeze machinery and a loud minimum-revision refusal, so that clients never silently misbehave across version skew.
28. As a developer, I want a full noun-verb CLI with UI↔CLI parity, contexts with an SPKI trust store, the universal output triad, and `run --` exec semantics, so that everything the UI can do scripts.
29. As a self-hosting developer, I want the web UI - matrix, reveal surfaces, app chrome, history, machine access, instance administration - matching the five locked prototypes and DESIGN.md tokens, so that the product feels like the frozen references on desktop and phone.
30. As a mobile user, I want every surface AAA-leaning - 44px+ touch targets, ≥4.5:1 computed contrast, state never color-only, full keyboard navigation - so that server-closet fixes work from the couch.
31. As a platform engineer, I want `definitions export | check | plan | apply` with digest+revision pinning and a `db | git` source-of-truth switch, so that project structure can live in version control.

Machine access & delivery

32. As a CI workload, I want OIDC federation (Kubernetes, Forgejo, GitHub Actions) with byte-exact binding instead of stored tokens, so that jobs authenticate without long-lived credentials.
33. As a self-hosting developer, I want service accounts with `hik_` tokens minted display-once through positively-exercised safe channels only, so that a bearer credential never lands in a shell history or log.
34. As a self-hosting developer, I want `hikyo run --` and rendered `env_file` delivery for Compose, byte-exact with named refusals for unrepresentable values, plus an expiring offline encrypted snapshot, so that my stack survives a Hikyo outage restart.

## Testing Decisions

The seams are locked in [mvp-boundary §1.1](https://github.com/Hikyo-Org/Hikyo/blob/main/docs/adr/mvp-boundary.md) - three executable check classes, nothing else counts as an acceptance criterion:

- **[E2E]** - scripted flows against a real server and real CLI, run on the full engine matrix (sqlite **and** postgres). No mocked server components.
- **[UI]** - Playwright flows against the embedded SPA, desktop + mobile viewports, assertions on computed state (including computed styles vs DESIGN.md tokens, axe-core serious/critical = 0), not screenshots alone.
- **[CI]** - the invariants the locked ADRs mandate (crypto ×16, isolation ×13 + 3 analyzers, audit registry completeness, oasdiff fail-closed gate, parity check, redaction fixtures, no-egress).

## Problem Statement

A self-hosted Hikyo instance is closed by construction: a human gets in only when an administrator hand-creates a local account or sends an invitation, and an external identity gets in only through generic OIDC with a brittle just-in-time policy (one string-equality claim, a zero-grant account, a generated handle) or through SAML plus SCIM. Teams that live in Google Workspace, Microsoft Entra or GitHub cannot offer their members "sign in with the account you already have", an invited member cannot claim an invitation with Google, and an operator who wants to let a known domain self-register (or, on a shared instance, let strangers land in their own organisation) has no switch that is safe to flip. An account created through a provider has no path to a local password or a second factor, so it can never clear a reveal ceremony. Nothing in the product can send an email, so a local email + password sign-up is impossible. The result is that every onboarding is an administrator's chore, and the seam a hosted deployment would need does not exist.

## Solution

Ship **social sign-in and operator-enabled open registration** as the first post-1.0 effort (owner decision 2026-09-03; the freeze-sensitive slice lands pre-1.0 as [Pre-freeze: retire JIT provisioning, move org.rename to manage-members@org, open the enums social sign-in grows](https://github.com/Hikyo-Org/Hikyo/issues/617)): Google, Microsoft Entra (tenant-specific OIDC provider rows) and GitHub (a new OAuth2-only identity kind) sign in beside local credentials and generic OIDC, and a **registration policy** (closed by default, at most one per org and one at instance scope, a standing delegation carrying an authority principal whose own permissions bound what the policy can grant) opens sign-up for admitted providers and, optionally, for local email + password through a real SMTP mailer. Sign-ups land by scope: an org policy applies a role template in that org; an instance policy lands the account nowhere or in a **fresh org** with the admin template. An invited member claims the invitation with a provider. A social-only account adds a password, TOTP or passkey through an `establish` round-trip. Every refusal is uniform on the wire and named in the audit trail. The CLI signs in through the ADR-locked browser handoff. Self-hosted first; positioning unchanged; this is the seam a hosted deployment could later use, not the hosted offering.

## User Stories

Registration policy (administrators)

1. As an instance administrator, I want an instance with no registration policy to be closed, so that nobody can create an account unless I explicitly open a door.
2. As an instance administrator, I want to create an instance-scope registration policy naming which providers may sign up and with which claim allowlist, so that only the identities I trust can self-register.
3. As an instance administrator, I want an instance policy to land sign-ups either nowhere or in a fresh organisation with the admin template, so that a shared instance can host strangers in their own tenant without touching mine.
4. As an instance administrator, I want a cap on how many fresh organisations one policy may mint, so that an open door cannot fill my database unbounded.
5. As an org member holding `manage-members`, I want to create an org-scope registration policy that lands sign-ups in my org with a role template, so that my colleagues join without an invitation each.
6. As an org member holding `manage-members`, I want my policy bounded by my own permissions, so that I cannot delegate a grant I do not hold myself.
7. As a policy author, I want the policy to be a standing delegation recorded against me as the authority principal, so that if my authority is later revoked, the policy goes inactive with cause `authority-lost` rather than continuing to act in my name.
8. As a policy author, I want write-time preconditions (public base URL configured, mailer configured for a local entry, provider carries the `email` scope) refused by name, so that I learn what to fix at save time rather than after a user hits a dead door.

## Implementation Decisions

All decisions are locked in the corpus; one line plus owning link each. The [decision index](https://github.com/Hikyo-Org/Hikyo/blob/main/docs/spec/social-signin.md#1-decision-index) is the complete map.

- **Registration policy**: one row per scope (0..1 org, 0..1 instance), subsumes and retires JIT, landing by scope, standing delegation with an authority principal re-checked on use, preconditions at write and use with inactive-with-cause, `signup` budget category, `registration.*` audit, reauth-gated mutations, editor on Members: [Grilling: registration policy](https://github.com/Hikyo-Org/Hikyo/issues/579), human-auth banner clauses.
- **Allowlists are child rows**, not JSON arrays, so the database refuses empty, duplicate and non-text values; the values-iff-claim cardinality rule is writer-enforced with a conformance pin (left for the owner, see Further Notes): spec section 14.13.
- **OAuth2 identity kind** for GitHub: closed profile enum, key `(oauth2, canonical origin, numeric id)`, own provider and transaction tables, PKCE S256 always, per-provider callback as the mix-up defence, verified email from the emails endpoint on sign-up only, sessions always single-factor, no OAuth2 reauth, third session FK: [Grilling: OAuth2-only identity kind for GitHub](https://github.com/Hikyo-Org/Hikyo/issues/580).
- **Intent** `sign-in | sign-up` as an optional field on a purpose-`login` start (absent = sign-in), recorded on both transaction tables; known identity signs in under either; unknown + sign-in refused `unknown-identity` with no registration event and no charge; start stays policy-blind: [Grilling: sign-in versus sign-up intent](https://github.com/Hikyo-Org/Hikyo/issues/604).
- **Admission gate before the charge** (synthesis reorder of the intent ticket's decision 3): policy present, active, provider admitted, evaluated before the `signup` budget; uniform response: spec section 14.2.
- **Verified-email assertion**: fixed recognised set `email_verified` or `xms_edov` as JSON boolean `true` beside a non-empty `email`, signed ID token only, never UserInfo; write-time 400 for an OIDC row without the `email` scope; one cause `no-verified-email` checked before the allowlist: [Grilling: per-provider verified-email assertion](https://github.com/Hikyo-Org/Hikyo/issues/598).
- **Provider departures**: Entra tenant-specific GUID issuer rows only (the `{tenantid}` template is a named reopen trigger); Google bare `iss` handled by the library's unconditional issuer check with the Hikyo belt deleted; NULL assurance policy = not reauth-capable, refused at start; pairwise `client_id` change refused by name: [Grilling: provider departures from the byte-exact issuer](https://github.com/Hikyo-Org/Hikyo/issues/588).
- **Invitation claim**: purpose `claim` on both kinds spends the credential-establishment authority through a federated round-trip; accepted only while the account holds no credential; `identity-exists` refuses without consuming; recovery-issued authorities never claim; `ErrNoInvitationPath` retired: [Grilling: invitation claiming by an OIDC or OAuth2 identity](https://github.com/Hikyo-Org/Hikyo/issues/582), spec section 14.4.
- **Establish and local factors**: social-only is a steady state; purpose `establish` proves local-credential creation only, carried as a session-stamped five-minute window spent by one mutation; new set-or-change password endpoint; unlink refuses iff no login credential would remain; link and unlink kind-agnostic under `proofSelection`: [Grilling: identity linking and credential adding for social users](https://github.com/Hikyo-Org/Hikyo/issues/586).
- **Local sign-up**: pending row plus reaper, no account until verification; full-entropy token in the URL fragment, GET never consumes; nullable UNIQUE canonical email on accounts; always `202` with exactly one send; verification re-checks the policy live, writes account + credential + landing, mints no session; consumed tokens read `unknown`; 24 h token: [Grilling: local email + password sign-up ceremony](https://github.com/Hikyo-Org/Hikyo/issues/584), spec section 14.3.
- **Email canonical form**: parsed addr-spec, ASCII domain lowercased, local part byte-preserved, ≤254 bytes, IDNA refused: spec section 2.5.
- **Fresh-org landing**: authority principal is the caller for org create + admin template inside one serialized transaction, identity row before org row; federated names `org-<id>`, local `org_name` on the form; org rename becomes `manage-members` at org; per-policy nullable cap, live count, cause `cap`: [Grilling: fresh-org landing](https://github.com/Hikyo-Org/Hikyo/issues/585).
- **Mailer**: SMTP-over-TLS only, `go-mail` behind a Hikyo package with a posture conformance test, synchronous send after commit, no outbox, durable mail intent and outcome events around every dial, "configured" is a static predicate, boot validates and never dials: [Research: mailer seam](https://github.com/Hikyo-Org/Hikyo/issues/583), spec sections 7 and 14.5.
- **Provider references** are `{kind, slug}` on every surface; the CLI takes `<kind>:<slug>` and a bare slug only when unambiguous: spec section 2.6.

## Testing Decisions

The seams are the three locked in [mvp-boundary §1.1](https://github.com/Hikyo-Org/Hikyo/blob/main/docs/adr/mvp-boundary.md); nothing else counts as an acceptance criterion:

- **[E2E]** scripted flows against a real server and real CLI on both engines (sqlite and postgres), no mocked server components. External identity providers are in-repo test doubles at the process edge, in the house style of the existing OIDC, SAML and WebAuthn doubles. Two new doubles: a **TLS SMTP sink** (generated CA passed through the CA-file variable, no cleartext path in any mode) and a **GitHub-shaped OAuth2 fake** (authorize, token with PKCE verification, `/user`, `/user/emails`); the existing OIDC double gains Google-shaped (bare `iss`, `email_verified`) and Entra-shaped (`xms_edov`, GUID issuer, `common` discovery) token fixtures.
- **[UI]** Playwright flows over the embedded SPA, desktop and mobile, with the S3 pinned assertion set (axe serious/critical = 0, text + ARIA for every state, focus, contrast, touch targets, computed styles against the design tokens). The closed flow registry gains the social sign-in family: login staged entry and doors, sign-up request and verify with the sink, Members policy editor, Security establish branch and password set, instance-admin OAuth2 CRUD and org origin filter, org rename. A locked surface without a flow fails CI.
- **[CI]** the registries that make a missing test a build failure: both-engine migration pin and directive parity, isolation suite with the third resolution member fixture-pinned, audit registry closure (`every_registered_type_is_actually_emitted` with a registration lifecycle including a mail intent with no outcome), bound registry rows with executable fixtures for every new value, parity dispositions for every new operation, contract chain and golden snapshots, known-env gate for the mailer variables, no-egress with and without a mailer configured, mailer posture conformance test.

What makes a good test here: it exercises external behaviour at the highest seam (real binary, real wire, real engine, fake at the network edge only), it cross-references the clause it proves, and it can never be satisfied by deleting or weakening its check. Uniform-refusal tests assert shape and timing parity between success and every cause, and read the cause from the trail, not the wire.

The **A7 row** in [mvp-boundary §1.2](https://github.com/Hikyo-Org/Hikyo/blob/main/docs/adr/mvp-boundary.md) **is** the test plan: implement its [E2E], [UI] and [CI] lists, do not re-derive them. Each ticket's acceptance checklist is a slice of that row. Prior art: the existing login, members, account and instance-admin Playwright flows; the OIDC federation isolation and audit lifecycle suites; the bound registry and budget totality tests; the parity test; the no-egress script.
