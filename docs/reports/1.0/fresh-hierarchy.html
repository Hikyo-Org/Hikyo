Atomic first-start key initialization

The signed-upgrade gate must not publish Healthy before the first key hierarchy exists. A crash after Healthy would otherwise leave a fresh installation unable to satisfy the next boot's read-only existing-key proof.

QuestionOptionsRecommended choice and reason
Where should first-start keys be created?Ordinary runtime startup after Healthy; separate generic write capability; narrow owned candidate transaction.Only Session.InitializeFreshHierarchy at the first Fresh/SchemaApplied operation, on its existing physical exclusion connection. All master, tier-3 and scope-generation inserts commit atomically before Healthy.
How should initialization release private material?Retain a runtime keyring; export a general concurrent Destroy operation; narrow crypto wrapper.A small crypto.InitializeFreshHierarchy wrapper invokes maintained LoadKeyring and zeros its temporary master, instance, token and scanning keys before returning. Root is consumed on every path. No runtime datastore or keyring escapes.
Should retries recreate missing or existing keys?Always initialize; accept partial inventories; fail closed and let the gate prove existing complete keys.Require both key tables empty and reject a second call, populated organizations/principals, legacy/restored/healthy state, stale operation and wrong phase. The gate uses CandidateKeys for existing hierarchy proof when a prior initialization committed.

Production writes use canonical generated SQLite/PostgreSQL queries inside one owned transaction, including the hierarchy-generation fence. The private KeyStore adapter refuses every unrelated method and validates exactly the initial instance, token and scanning key set.

Actual SQLite and dedicated PostgreSQL tests initially passed in 3.382 seconds. Expanded validation includes a real scope-insert conflict after partial hierarchy inserts, injected precommit failure, zero retained rows after both failures, successful actual AEAD opening, wrong-root refusal, second-call refusal, populated and legacy refusal. Expanded actual both-engine race passed in 22.975 seconds. Crypto, uncached architecture boundary and lint passed in 0.405, 7.449 and 33.488 seconds; scoped vet passed. These are local results; candidate CI and signed delivery remain parent-owned.
