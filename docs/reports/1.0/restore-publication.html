Restored SQLite databases require durable directory publication

Base 353e724d9b09e418fc3fd8ce665fe6307813dec3, PR #655. This report records the local repair and validation. It does not claim a merged release, production power-loss testing, or implemented signed upgrade foundations.

Defect and resulting behavior

Restore synchronized the staged database and hard-linked its final name, then returned success without synchronizing the directory. The final name could be absent after a crash despite successful file synchronization. Restore now synchronizes the complete resolved directory ancestry after the no-overwrite link. An existing directory is not evidence that its ancestor entries survived an earlier failed or concurrent operation.

If any directory sync fails, the restored target remains available with its committed recovery epoch changes. The error names that target and reports durability as unconfirmed; the store returns an empty manifest. Existing app error branches stop roll-forward and retain failed drill targets even with cleanup requested. The temporary staging names remain exclusively owned and are removed. A retry refuses the existing final target.

Which directories need synchronization?A: complete resolved ancestry every attempt; B: only the leaf; C: stop at the first existing directory.A. Existence cannot prove ancestor durability after prior failure or concurrent creation. Errors propagate instead of assuming durability.
