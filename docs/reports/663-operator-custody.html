#662/#663: installation operator custody

Decision record, 5 September 2026. Signed upgrade compatibility ADR remains authoritative.

Decisions

Question and optionsRecommended choice and reason
Pin operator key in pending DB attestation, or installation storage?Separate durable HIKYO_UPGRADE_STATE_DIR/operator-custody.json. Current public key and monotonic epoch floor survive replacement of the database. Configured public key must match this installed pin, including healthy restarts with no backup evidence.
How to establish initial custody?Fresh boot writes the configured public pin before database mutation, binds generated instance identity immediately after bootstrap. Pre-ledger backup export may establish initial custody only after authenticating the actual legacy source against the signed catalog. An existing ledger cannot recreate missing custody.
How to authorize rotation?Prior-key signature by default. Explicit local break-glass requires proposed-new-key signature and root-key escrow proof against existing encrypted hierarchy. No private operator signer or escrow material enters HTTP/server configuration.
How to coordinate external state and database commit?Acquire the DB writer/control-row lock and recheck source plus strongest epoch, fsync an atomic external journal before mutation, then apply exact journaled state; atomically publish new pin after DB commit. An incomplete journal blocks admission. Repeating the exact local command accepts either exact pre-commit or post-commit state and never creates a second incarnation. If credentials advanced after a pre-commit crash, a fresh authenticated request may replace only an uncommitted journal whose complete DB authority still matches its recorded source; committed journals require the exact original request.
How to recover an archive older than operator rotation?Retain current external key. Ordinary prior-key rotation refuses historical DB epochs below the external floor. Explicit local escrow-proved break-glass advances beyond max(canonical restored credential inventory, external floor), creates a new incarnation, increments generation and invalidates all pending evidence. Retired archive keys never become authority.

Local command

hikyo upgrade operator rotate --statement rotation.json   --signature rotation.sigstore.json --new-public-key next.pub
# Explicit local break-glass additionally requires:
# --local-break-glass --root-key-file root-escrow

The signed statement binds actual instance, restored incarnation, restore epoch, strongest known credential epoch, next epoch, current and new key IDs and issue time. For historical restoration, strongest known epoch includes the durable external floor. After success, update the configured public-key mount to the new public key. Maintenance remains until fresh recovery evidence and candidate health pass.

Validation

GOMAXPROCS=2 go test -p 1 ./internal/upgradegate -run TestOperator -count=1 -json: 17 cases passed, zero skipped, real SQLite and PostgreSQL, 8.319 seconds. Evidence: /tmp/hikyo-runtime-fence-evidence/operator-rotation.jsonl and operator-rotation-summary.json.

Coverage: fresh pin without evidence; wrong/missing/configured replacement custody; signature spoof; replay; strongest epoch and incarnation invalidation; missing/wrong/correct root escrow; injected failures after actual fsynced journal and committed DB boundaries, followed by exact resume; fresh authenticated replacement after a pre-commit crash and concurrent credential-epoch advancement; symlink/mode refusal; historical restore after two genuine rotations, retaining retirement of the old signer.

Operational requirements

State directory must be persistent, owned by the process identity, mode 0700. Custody and lock files require mode 0600 and one link. Replicas sharing a database must share coherent POSIX flock, atomic rename and fsync semantics for this same state directory. Database restore must preserve this directory. Linux and macOS are supported; other platforms fail closed for production custody.

Windows scope is established policy: internal/crypto/client_secure_windows.go:14-19 explicitly identifies Windows as a client platform and Unix as the server host; internal/disclose/file_windows.go:47 says Windows is not a bootstrap host. The prior F4 custody decision in docs/reports/1.0/upgrade-attestations.html likewise limits operator custody to supported Unix hosts while preserving Windows client builds. This implementation preserves that boundary.

Windows client proof: GOMAXPROCS=2 GOOS=windows GOARCH=amd64 go build -p 1 -o /tmp/hikyo-runtime-fence-evidence/hikyo-windows.exe ./cmd/hikyo passed. The upgradegate test executable also cross-compiled. This is compilation evidence, not native Windows execution.

Focused tests do not claim full release CI, signed-commit verification, preview deployment or production deployment. Parent lifecycle owns those gates.

R3 integration correction

Public backup and reconciliation entrypoints now acquire external public custody before datastore exclusion, validate the actual instance and epoch floor before direct runtime/recovery admission, and refuse incomplete journals or mismatching configured keys. Ordinary data restoration holds the same custody scope. These flows remain root-free. An escaped custody capability becomes invalid at callback exit.

Focused existing ordinary export, data restore and status plus new production-config refusals: 10 cases passed, zero skipped, actual SQLite and PostgreSQL, 7.463 seconds. Evidence: /tmp/hikyo-runtime-fence-evidence/backup-custody.jsonl. Wrong signer and unfinished journal cases prove refusal before database or writer-lock creation.
