Executive verdict

Changes recommended; not a clean security certification. The most important finding is a mismatch between the possession-first account-security policy and password-first proof selection. Fix that boundary before treating enrolled MFA as protection for persistent credential changes.

The next tier concerns reclaimable-storage accounting, frontend freshness and liveness, unbounded revision reads, and operational signals that report unknown state as healthy zero. These are specific defects or assurance gaps, not a judgment based on file length or suspected AI authorship.

  • Security: strengthen credential-mutation proof selection; state exactly what dynamic-secret TTL guarantees.
  • Reliability: make reconnect, cancellation, startup preferences, and unavailable measurements explicit.
  • Performance: bound work by current/page size, not lifetime history.
  • Maintainability: consolidate already-divergent helpers and close static-check coverage gaps.
How to read the confidence labels

Source-confirmed means the implementation and its relevant callers support the finding; it does not mean a runtime failure was reproduced. Scaling risk means query/work growth is visible but latency and capacity impact are unmeasured. Assurance / guardrail gap means a promise or check is incomplete, without a demonstrated bypass. Severity reflects the narrowed impact after skeptical review.

F01

Credential mutations prefer password over eligible possession factors

HighSecurity · Source-confirmed policy mismatch
Evidence
internal/service/webauthn.go:1197-1207 selects the password immediately when present, before considering TOTP, and does not evaluate other passkeys. Enrollment/removal call this selection at :155 and :1062. TOTP mutation paths use password-only proof at internal/service/factors.go:288-297 and :516-525.
Impact
With an authenticated session and valid password, credential management can proceed without proof from an independent eligible possession factor. That is weaker than the intended protection for persistent credential changes.
Counterevidence
Initial factor enrollment can legitimately use password proof. The credential being removed is excluded from selection; removal of the only possession factor is not itself evidence of this defect. Ownership checks, session invalidation and auditing remain enforced. No unauthenticated-access claim is made.
Policy / tests
docs/adr/human-auth.md:178 requires possession-first selection. The exclusion clarification is at docs/handoff/54-human-auth-full.md:390-394. internal/isolation/webauthn_e2e_test.go:727-728 expects password-authorized enrollment of a second passkey, encoding the weaker behavior rather than refuting it.
Recommendation
Centralize purpose-bound proof selection over eligible, pre-existing credentials, excluding the mutation target. Allow password fallback only when no eligible possession factor remains. Extend mixed-factor policy coverage without weakening existing authentication or audit checks.
F02

GC cannot reclaim parameter-contract bytes charged to publish quota

MediumStorage · Source-confirmed accounting mismatch
Evidence
internal/store/queries/postgres/retention.sql:52 and internal/store/queries/sqlite/retention.sql:49 collect entries but retain snapshots.parameter_contract. Accounting at internal/store/queries/postgres/revisions.sql:328 and SQLite :276 still charges those contracts regardless of payload collection.
Impact
Repeated publications with nonempty contracts accumulate quota-charged bytes that retention changes and unpinning cannot free. Publish refusal can persist after eligible ciphertext is collected, despite the recovery advice in internal/service/publish.go:1386-1388.
Counterevidence
Contracts are intentionally immutable metadata, bounded to 256 KiB each by internal/parameters/parameters.go:18. Retention itself may be correct; coupling permanent metadata to a reclaimable-payload quota is the mismatch. This is not retained secret plaintext or an irreversible instance failure.
Recommendation
Resolve the metadata contract first: either collect contracts as payload, or retain them with separate permanent-metadata accounting and truthful quota guidance. Do not clear immutable metadata in a speculative one-line patch. Verify accounting before and after GC for parameterized snapshots.
F03

SSE recovery and fallback do not ensure matrix cache convergence

MediumFrontend · Source-confirmed freshness gap
Evidence
web/src/api/advisory.ts:195-202 marks the stream healthy on frames, disabling fallback at :156. The initial retry frame is sent at internal/server/revisions.go:480. Recovery performs no catch-up invalidation at web/src/api/matrix.ts:525-534. Signals fallback refreshes values at :586-590, but pending-draft queries at :607-618 have no equivalent refresh.
Impact
Changes missed during disconnection can remain absent after reconnection. During fallback, a refreshed pending marker can lack its corresponding current draft preview.
Counterevidence
Drafts load initially and are invalidated by named SSE events and local mutations. Values can recover through disconnected polling. Server version checks preserve publish integrity; stale UI does not establish stale-write acceptance.
Policy / tests
docs/adr/system-architecture.md:129 requires authorized refetch on recovery. web/e2e/flows/matrix.spec.ts:510-540 checks recovery request behavior, not convergence after missed changes.
Recommendation
Reconcile signals, values and pending drafts before declaring recovery complete. Refresh drafts during fallback too. Verify eventual cache convergence across disconnect/reconnect and another session's draft changes.
F04

Revision history loads all revisions with per-revision change queries

MediumPerformance · Unbenchmarked scaling risk
Evidence
internal/service/revisions.go:127-146 loads every snapshot, then calls Changes once per revision at :137. internal/store/queries/postgres/revisions.sql:138 has an unbounded snapshot projection including parameter contracts that conversion discards at internal/store/repos_revisions.go:1527.
Impact
R revisions require R additional change queries, full-history allocation and an unbounded response. GC preserves lineage, so payload retention does not bound this endpoint.
Counterevidence
Publisher-name lookup is cached per request. MCP has a bounded history path at internal/service/mcp_page.go:198; the finding concerns the unpaged history surface, not all revision access. No latency or memory benchmark was run.
Recommendation
Use the existing page-reading seam, batch changes for the selected page, and omit contracts from metadata projections. Measure query counts, response bytes and latency at increasing history sizes.

F06

Workspace handoff has unbounded network phases

MediumFrontend · Source-confirmed liveness gap
Evidence
web/src/api/workspace.ts:284-315 supplies neither a deadline nor a caller signal to remoteJSON, including body consumption. Preparation at :501,522 and redemption at :564-569 use it. web/src/routes/useWorkspaceHandoff.ts:53-60 keeps actions disabled until settlement.

F07

Dynamic credential expiry is not an established-session deadline

MediumSecurity · Assurance gap
Evidence
internal/dynamic/postgres/postgres.go:266-278 sets password validity. Revocation at :281-282 deletes the role without an explicit established-session lifetime mechanism. Broader expiry wording appears at docs/site/src/content/docs/docs/dynamic-secrets.mdx:21-22.
Impact
An operator may interpret a lease TTL as a deadline for all database access, including existing sessions during a Hikyo outage. The implementation establishes password-expiry behavior, not that stronger access deadline.
Counterevidence
PostgreSQL VALID UNTIL is password expiration, not role expiration. Preventing new password-authenticated connections after expiry is a valid guarantee. internal/dynamic/postgres/postgres_integration_test.go:122-130,146-158 checks catalog validity and role removal, not termination of existing sessions.
Recommendation
Separate password expiry, role cleanup and active-session lifetime in the documented contract. If a hard offline access deadline is required, design independently enforced database/proxy session controls; Hikyo-driven cleanup alone cannot guarantee this during Hikyo downtime.

Evidence

Impact / limit

F17

Evidence

Architecture, duplication & “slop” assessment

What is working

  • Authorization chokepoints, scoped repositories and transaction ownership are real executable mechanisms, not only documentation.
  • Boundary checks include test imports; custom analyzers have negative fixtures at internal/boundary/boundary_test.go:175-182 and internal/lint/lint_test.go:67-86.
  • Separate committed-order audit export and writer barriers address a subtle PostgreSQL concurrency issue.
  • Sensitive UI operations have owner/unmount guards; remote caches are keyed by origin and session.
  • Generated freshness checks include new untracked output at .github/workflows/ci.yml:514-527. Frozen installs, pinned actions, Go vet, vulnerability scanning and both Storybook themes are wired.

Where complexity is leaking

  • Adapters repeat parsing and lifetime rules, then diverge: WebAuthn conversion, cache teardown, atomic writing and installer bounds.
  • Comments can overstate actual guarantees: password-first proof is described as account-security proof; optional theme persistence is a startup dependency; unknown metrics are intentionally emitted as zero.
  • Historical metadata is durable by design, but several readers treat it as a bounded working set.
  • Large route modules combine orchestration, reusable hooks and multiple domain panels, making ownership harder to reason about.

No AI-authorship inference. “Slop” is used here only for concrete misleading guarantees, unnecessary duplication and weak ownership. Generated SQL/client code is not labeled duplicate-code debt. No numerical whole-repository clone score was produced, and the review does not establish a history of tests or rules being deleted to pass CI.
