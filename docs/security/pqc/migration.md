# Migration policy, draft v0.6

Status: **owner decided and security approved, not operative**.
Policy and requirements for DEC-11 to
DEC-16, DEC-19 and DEC-20 in the
[register](../../adr/post-quantum-migration.md#decision-register). This file
states constraints on the child tickets; it designs no protocol. Nothing here
authorizes key generation, rotation, trust activation, provider mutation,
release or deployment. Where no quantum-safe answer exists it says so, with the
residual risk (an exception row, E-nn) and the claim it limits. Algorithms are in
[profiles](profiles.md); `Inn` in [inventory](inventory.md).

## Order of operations (per surface)

A step starts only when the previous gate is met and recorded. Gates name what
can be observed: first-party nodes and tools the operator controls can be
measured; third-party, offline and already-installed copies cannot, and floors
are local claims, not signature authority (`internal/releaseidentity/floor.go:5`).
That limit is registered (E-17).

| Step | What happens | Gate (observable) | Abort |
| --- | --- | --- | --- |
| 0 Decide | Owner and security decisions recorded; ADR amendment landed | Receipts; no HOLD on the surface | Nothing deployed |
| 1 Keys | Generate and escrow new keys ([below](#key-generation-and-escrow)) | Escrow drill restores a fixture | Destroy only never-used test keys |
| 2 Readers first | Release first-party readers, verifiers and offline tools that can parse and verify the new format while still writing the old one | Frozen legacy fixtures pass on first-party nodes and tools; unknown versions refused; operator attests the readers it does not control | Revert binary |
| 3 Authenticated trust | Distribute public keys through an authenticated path (receiver pin, operator-installed rollout enrollment); release-trust bootstrap is an open gap ([below](#release-trust-and-install-paths)) | Independent check recorded outside the datastore | Writers stay disabled |
| 4 Writers, compatibility | Writers emit the new format as configured; old readers keep working | Mixed-version matrix on first-party nodes | Switch writers back |
| 5 Strict and floor | Operator selects strict; old writers refused; the rollback floor is raised when the first strict writer is enabled | Enforcement evidence ([profiles](profiles.md#configuration-downgrade-rollout-exceptions-dec-10)); downgrade attempt refused | Lower the profile; the floor is not lowered |
| 6 Retire | Retire classical keys only when [eligible](#retirement-eligibility); rotate secrets that crossed classical hops ([below](#prior-exposure)) | Eligibility met; owner decision recorded | Forward only |

## Key generation and escrow

| Rule (DEC-12) | Detail |
| --- | --- |
| Where | On the operator or custodian host through protected input and disclosure paths; no private key in argv, logs, audit, receipts or errors; the dangerous-print escape is never used in evidence. This contract generates no key |
| Forms | Backup and receiver identities are 32-byte seeds in text form; ML-DSA keys are 32-byte seeds (seed-only PKCS#8). A seed is the whole key |
| Escrow | Backup identity in a failure domain separate from the root key and datastore (existing ADR). With one maintainer that means separate storage and access control, not separate people |
| Custody | Software custody only; no production HSM or KMS is assumed |
| Entropy | `crypto/rand`; imported keys are not accepted for new strict material unless generated by the maintained tool |
| Overlap | The old key stays in the read set. The custody vault has one `backup_identity` field (`vault.go:50-56`), so keeping the old identity needs its own escrow or a vault format change: a #1126 requirement |
| Scanning | The vendored scanner rule matches `AGE-SECRET-KEY-1` plus 58 characters only (`internal/scanning/rules/vendor/gitleaks.toml:57`), so `AGE-SECRET-KEY-PQ-1...` is not matched: a #1126 requirement; the file is not edited here |

### Operator custody vault (`operator.age`, I08)

Facts: the record holds the backup identity, P-256 attestation key and **root
escrow** (`vault.go:55`), sealed by age scrypt. Unattended flows seal it with a
secret derived from the root key; the code accepts any nonempty secret up to
1024 bytes, so a human passphrase has unverifiable entropy. The only rewrap
caller migrates a legacy passphrase vault (`automatic_upgrade.go:372`) and
preserves the record (`vault.go:155-157`). Drills use the vault's escrowed root
(`automatic_upgrade.go:420`). `rotate-root-key` does not re-seal the vault.
A root-sealed record cannot recover the root it is sealed with; a passphrase-sealed
record can yield a lost root, which is another reason its entropy matters. The record is bounded by age's 16-byte
file key. Consequences, stated for the owning child (#1126), not designed here:

* Old passphrase-sealed copies hold a live `root_escrow`, so retiring them needs
  a root rotation, and old identities keep opening historical archives.
* Option (a), keep age-scrypt and `Rewrap`: `Rewrap` keeps the record, including
  any stale escrow that drills then use; removing the passphrase prompt strands
  hosts whose migration was interrupted.
* Option (b), seal with the existing 256-bit envelope keyed from the root: lifts
  the record off the category-1 floor; new file format and reader-first
  migration.
* Under either option `rotate-root-key` does not re-seal, so after it the new
  root's secret fails with `ErrUnlock`, which is then read as a passphrase vault
  (`automatic_upgrade.go:357-364`); the vault-generated identity and attestation
  key are stranded. Requirement on #1126: re-seal during root rotation before any
  flow here relies on rotating the root.
* Either way a vault holding root escrow must not be used where identity and
  root must stay in separate domains.

DEC-12 records the options; the "fields keep 256-bit protection" statement does
not apply to this record, or to any field while a copy holding a root that opens it
exists, because its `root_escrow` opens the whole hierarchy.

## Mixed paths and archive provenance

**A PQ-protected object has no independently sufficient classical door, in either
mode.** An object is PQ-protected when written with hybrid recipients. Hikyo's
writers never add another stanza, and Hikyo's readers refuse a header with a
classical, scrypt, ssh, plugin or unknown stanza beside a hybrid stanza at restore
and preflight. That refusal binds Hikyo only: age's decrypt path has no label
check, so another tool holding a classical identity opens such a header. No classical recipient is added "for
recovery". A separate classical archive of the same data is a classical door to
that data (E-10). Recipients beyond one exist only for distinct retention
classes (operations spec); 32 is a ceiling, not a target.

**Archive provenance.** Anyone holding a public recipient, classical or hybrid,
can write an archive for it: the restore code already states that an archive is
forgeable by anyone holding the public recipient (`internal/store/authn/restore.go:91`),
and age has no sender authentication. Requirement on #1126 and #1132, symmetric
for hybrid and classical archives: where an operator has selected strict for
backups, an archive is restored only if its provenance is bound to a receipt,
checked **before** any re-encryption; otherwise it is quarantined. This does not
apply to default compatibility restores (DEC-05), and frozen classical archives
stay recoverable there. Today only `upgrade-export` writes a receipt
(`internal/service/backup.go:250`), and a receipt is an unsigned public marker
(`internal/backupreceipt/artifacts.go:138-146`) whose signed attestation lasts at
most 24 hours, so a forger can mint a matching one. Requirements on #1126: every
export path emits a receipt and provenance binds to a signed record. The receipt
signer, the pin and the release from quarantine are **not designed here**.
Existing restore holds are cleared by the host-local `restore reconcile`
(`internal/app/backup.go:108`), so any new hold is presumably clearable by
whoever has host access. Residual risk (E-19): no provenance or integrity claim
for an archive restored without a signed receipt; the strict backup profile stays
HOLD until every export path emits one and `restore run` and `restore drill`, which
today take no receipt (`internal/app/backup.go:328-343,716`), accept it.

**Re-encrypted copy.** "Rewrapped" means authenticating the old archive to its
final chunk and writing a new archive from the plaintext stream with a fresh
random file key and hybrid recipients. Keeping the old file key or header leaves
the payload open to anyone with the old header and a classical identity. The old
archive stays a separate object with its classical door until destroyed.

## Retirement eligibility

"Retire" removes a key from the write set; "destroy" deletes private material.

| Criterion (all required, DEC-11) | Why |
| --- | --- |
| No retained archive, receipt, signature or ciphertext needs the key without a re-encrypted or countersigned copy the owner has recorded as sufficient | Historical access |
| First-party readers and verifiers are at or above the floor; the operator attests the rest | No stranding |
| The owner-set retention window has elapsed; retention health shows no uncertain-custody exception | Existing retention rules |
| Compromise recovery does not depend on the key | Recovery |
| Every copy of the key and every archive protected only by it is inventoried | Re-encryption cannot revoke attacker-held copies |
| Owner decision recorded with an evidence reference | Absence of a decision is not permission |

Destroying a live key erases nothing already written to a retained backup.

## Rollback floor and historical verification

| Item | Requirement (DEC-11) |
| --- | --- |
| Floor | Per surface: minimum reader version, format or profile version, trust generation, raised at step 5. Outside strict the format floor does not make a frozen historical archive unrestorable; where strict is selected, receipt-or-quarantine applies to it (E-19). A binary that knows the floor and is below it refuses the surface before any write or authority use; a binary built before the floor existed cannot refuse (E-17) |
| Persistence | The floor must survive a restore. Because a persisted floor is an untrusted local claim (`floor.go:5`), where it is kept and how a fresh host obtains it are #1126/#1132 requirements; until stated, strict claims are unavailable on a host without an operator-established floor (E-17) |
| Rollback | Only to a build at or above the floor with valid trust and retained custody; never by stripping PQ verification, re-enabling a revoked key or destroying retained keys |
| Historical classical verification | Classical signatures written before a surface moves to PQ-required remain checkable read-only for integrity. After a quantum break they are forgeable, so no non-repudiation or backdating claim is made for classical-only evidence (E-12). Countersigning retained evidence is an option for the owning child (DEC-11), not specified here. Audit exports have no chain and are forgeable by a datastore writer today (`docs/adr/audit-model.md`), so they carry no claim; #1135 records that |
| Unknown algorithm or generation | Refuse |

## Compromise recovery and restoring policy

| Event | Policy |
| --- | --- |
| Any trust change (revocation, key replacement, floor or generation change) | Requires every required algorithm of the current pinned set; one remaining algorithm alone cannot replace the other (a downgrade path). If a required key is lost, recovery is an offline reinstall from an independently verified source (#1135). Losing the sole ML-DSA recovery key leaves no PQ-signed reinstall signer (E-18) |
| Signing key compromise | Revocation follows the surface's existing rule (PKI CRL, Transit compromise rules, webhook generation change) |
| Receiver or backup identity compromise | New identity and generation, fresh PQ archive; the old identity still opens historical copies |
| Classical authority broken by a quantum adversary | Remote classical-authenticated updates are untrusted; offline reinstall |
| Restore | Recovery holds are reinstalled; revoked authority is never revived; pre-restore attestations cannot reactivate authority |
| Interrupted migration | Reconcile the exact failed step; never finish by falling back to classical behavior |

### Prior exposure

Credentials and values that crossed classical-only hops before a surface became
strict are treated as exposed to a recording adversary; step 6 rotates the
long-lived ones after the surface is strict. A rotated credential delivered again
over a compatibility hop (I14, I16) is exposed again (E-07). Plaintext already
delivered cannot be recalled.

## Dispositions (DEC-13 to DEC-16, DEC-19, DEC-20)

Accepted as recommended on 2026-11-02. Owner: Marc Went. Not operative; see the
[register](../../adr/post-quantum-migration.md#decision-register).

### Pairing and remote proofs (I20)

2048-bit SRP and Ed25519 DPoP; no standards-backed maintained PQ PAKE in the
pinned dependencies; `go-jose` v4.1.6 has no ML-DSA; a JOSE ML-DSA identifier's
status was not checked. Decision: #1130 stays HOLD (E-01). Hybrid TLS
stops **recording** of the exchange; it does not stop an **active** forger of the
classical pinned leaf, who captures the SRP transcript. Pairing pins are read over
a classical chain unless the operator supplies an override
(`internal/remotefetch/pairing_identity.go:58`), so a read pin is only as authentic
as that chain. No quantum-safe answer exists; claim limited: no PQ
authenticity, pin or password-exchange claim for pairing. Not recommended: a
KEM + SRP composition (forbidden by the issue) or ML-DSA JWS now (no library path).

### Release trust and install paths

Source facts: P-256 primary and recovery keys; the recovery key signs root,
policy, bridges and the legacy-track metadata and catalog; the Sigstore keyless
workflow identity signs stable metadata and catalog (`snapshot.go:139,180`);
nightly, its manifest and its Helm chart are keyless (`.github/workflows/nightly.yml`), while the
installer checks nightly metadata and catalog with `openssl` against the P-256
recovery key (`install/upgrade-nightly.sh:115`) and the manifest with cosign
(`:382`); the pinned-key parser rejects ML-DSA; pinned trust carries no floor input
(`internal/selfupdate/trust.go:186`). `sudo hikyo upgrade` accepts only nightlies
(`internal/app/automatic_release.go:26,45`), verified keyless only
(`releasetrust/nightly.go:325`); a replacement image verifies itself with its own
stamped trust (`internal/app/unattended_upgrade.go:81`); gates refuse a changed
release root (`upgradegate/gate.go:126`, `app/upgrade_gate.go:180`); fresh
installs receive the install script and trust anchors over classical HTTPS
(`install/install.sh.in:6-12`, `upgrade-nightly.sh:3`), authenticated only by
classical pinned verification. That legacy channel guarantees classical
integrity of the downloaded bytes and nothing against a quantum adversary.

| Document or artifact | Signer today | PQ signer (DEC-14) |
| --- | --- | --- |
| Root, stable policy, bridges, legacy-track metadata and catalog | Recovery key (P-256) | ML-DSA recovery key, all-required with the classical key |
| Stable metadata, catalog, manifests; packaged chart image policy (keyless mode, `.github/workflows/release.yml:633`) | Keyless workflow identity | Keyless unchanged (E-03) plus a maintainer-held ML-DSA signature at the local publish step ([stable workflow signing ADR](../../adr/stable-workflow-signing.md)) |
| Releases signed with the primary key before keyless; the in-tree chart `primary.pub` (keyed mode) | Primary key (P-256) | None: historical verification only (E-12) |
| Nightly track and image-replacement paths | Keyless; own stamped trust | None (E-15) |

Requirements on #1132, stated, not designed: every trust document needs a
PQ-capable form valid only when the pinned required set verifies; the parser must
learn ML-DSA; progression is **sequence-only** (`releasetrust` has no clock, so no
cutoff date is proposed); a PQ claim is made only after a persisted verification
that required every algorithm; and #1132 must close or register **every**
binary-replacement path (stable, nightly, `sudo hikyo upgrade`, unattended image
replacement, chart image policy, fresh install). The **PQ trust-anchor bootstrap
is an unsolved gap**: a classically signed release or statement that introduces
PQ keys is forgeable by a quantum adversary, hosts that never receive it or sit at
the pre-PQ generation cannot reject forged classical documents, and whether PQ key
hashes can reach existing installs at all is an open #1132 feasibility question
(changing the embedded root bytes makes the gates above refuse). Claim limited
(E-11, E-15): **the PQ release-authenticity claim stays HOLD** until #1132 closes
every replacement path; no per-host or per-track claim is made meanwhile. A forged
classical update replaces the verifier behind every other authenticity surface, so
E-11 and E-15 limit those claims too. The ML-DSA recovery key's custody is not
yet named: HOLD under DEC-14 until the owner names it before #1132. Losing it is E-18.

### Sigstore and classical supply chain (I26, I27, I31, I32)

Fulcio, Rekor, cosign, Kyverno image verification, Apple codesign and
notarization, OS packages, commit signing and the Go checksum database stay
classical. The sigstore library has ML-DSA support, but no statement that the
public-good service issues PQ certificates was read. E-03: a first-party PQ
signature is required in addition, never instead; no claim these ecosystems
migrated.

### SSH, federation, authenticators (I25, I17-I19)

OpenSSH has PQ key agreement (`mlkem768x25519-sha256`, default since 10.0) but no
PQ signatures (page fetched 2026-11-02); Hikyo should not emit the `@golang.org`
ML-DSA certificate names, which no specification defines (E-02). OIDC and SAML
signing algorithms are RSA and ECDSA, controlled by the IdP (E-04). The WebAuthn
library verifies ML-DSA keys on go1.27; authenticator support is unchecked (E-05).
GitHub requires libsodium sealed boxes: no replacement, no second wrapper (E-06).

### Rollout authority (I23) and PKI root (I24)

#1131 says to bootstrap PQ trust "through the existing authenticated authority".
Source: the controller trusts one operator-installed Ed25519 public key file
(`cmd/hikyo/config_rollout.go:26`), shipped by the chart as an immutable
ConfigMap (`chart/hikyo/templates/rollout-custody.yaml:40-47`), not a Secret; no
in-band key transition exists; the controller cannot check the coordinator's MFA
(`transport.go:137`). DEC-20 states the options and flags that option (c) departs
from #1131's wording. Requirements on #1131, not designed here: a new key or id
fails `verifyCommand` on the existing journal (`controller.go:60`), and emptying
the journal Secret resets the accepted sequence and loses the plan that Restore
needs (`controller.go:82`). Residual (E-14): enrollment trust is cluster access
control and replay protection holds only against actors without journal write.
PKI (DEC-19): a classical root over an ML-DSA intermediate is not a
PQ-authenticated chain; provisioning the root is the owner's decision.

### Operator pin rotation (I08)

A prior-key rotation is verified against the current P-256 pin
(`backupreceipt/operator.go:150-165`), so a forged P-256 signature rotates the
pin; local break-glass is signed by the new key itself and needs local recovery.
Claim limited: operator attestation authenticity is classical (E-16).
