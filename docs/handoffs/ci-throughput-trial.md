# CI throughput trial: PR #916

The hosted pilot supports adopting single-pass shard planning and retaining the existing trusted-main compiler cache. Compiling a race-test binary once is promising within each existing runner, but transferring it to a separate runner did not establish a latency win. No extra runner capacity, paid service, review bypass or reduced test inventory is proposed.

The hosted pilot concluded on 2026-10-14 with all four experiment jobs passing. The temporary experiment workflow, Python harness and cache-policy exception were removed. The production change is single-pass planning with a trusted-base migration. This report records that experiment and its source revisions; current review, validation and delivery status belongs to PR #916.

| Transfer compiled race binaries between runners | Build once, upload an exact-source binary and consume it in a separate read-only job. | Upload 5s, download 1s, six executions 6.6093s; the consumer also waited 30s and incurred setup/checkout costs. | Do not add a separate producer/consumer stage based on this pilot. These measurements cannot be added together into an overall speedup: planning belongs to full validation, the cache comparison is feedback compilation, and binary reuse is a one-test race pilot. Queueing and review remain separate parts of PR-to-merge latency. The cache experiment itself waited 368 seconds after its dependency completed, illustrating that shorter execution alone does not eliminate capacity contention.

## Production change and trust boundaries

The `all` planner command emits complete race, fuzz and isolation plans after one package-inventory read. Individual planner modes remain available. CI loads planner code from the trusted base, builds it once and checks its protocol capability. The first candidate permits fallback only to the exact known legacy source digest. Unknown source, failed bulk execution, malformed JSON and empty shards fail closed. Once the reviewed bulk planner is on the trusted base, CI uses its single-pass protocol.

Current main `e5baadde8c0d8d393dabc27003bf125fd48444f2` adds security validation and release-tag handling. The conflict resolution retains both sets of inventory checks and mutation regressions. It also retains main's release caller guard and tag-ancestry validation. The planner fixture now covers the inherited release-tag execution path while leaving the original legacy fixture and frozen coverage fingerprints unchanged. Hosted timing claims above remain bound to the earlier measured source; they are not timings for main's expanded security inventory.

## Failures, corrections and validation

The original [Go feedback job](https://github.com/Hikyo-Org/Hikyo/actions/runs/38558624639/job/115833890514) failed with ShellCheck SC2148 because two new embedded shell fixtures lacked a shell declaration. This reproduced locally. The correction requires a Bash shebang and removes only that exact header before byte-exact workflow comparisons. No lint suppression was added. The corrected Go feedback lane passed locally in 13s, the full `scripts/ci` regression package passed 1,365 test/subtest events, and both hosted feedback lanes passed on `7f594d7b36a89c02d5a223aa6f7c8f538d2a07ed`.

After main advanced, [queue check 116092043731](https://github.com/Hikyo-Org/Hikyo/runs/116092043731) failed. Publisher run `38633821318` explicitly recorded `PR validation gate [merge-conflict]` for that head. The first merged regression run then caught the release-tag fixture mismatch in the migration and coverage tests. Both failed attempts are retained. Updating the exact fixture and adding the release-tag execution case made all focused migration and conservation checks pass in 8.010s.

Final cleanup validation passed: both Go packages reached terminal PASS with 1,556 passing test/subtest events and zero failures (planner 5.010s, CI policy package 69.417s). The actual Go fast-feedback lane passed in 16s, including ShellCheck and pinned actionlint, and the unchanged cache-policy check passed. Independent Sol review found no remaining issues in the merged safeguards; measurement interpretation was reviewed separately. Cross-provider review has not been performed. Queue admission success is not complete current-base merge proof; full protected-queue validation and required review still apply before any merge.
