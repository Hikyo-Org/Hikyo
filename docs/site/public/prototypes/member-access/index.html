member access & granularity

Members want access finer than scope level: only some keys, folders or key groups, per capability. Where does that grain live, and on which page is it authored and read back, without the Members page drowning? Explores an amendment: key and folder grants are "deferred (fog)" in the locked permission ADR.

  • 6Widening moves need confirmation Verdict on 5: option A. Moving a key so that someone's except no longer covers it opens a confirmation naming who gains and who loses access; cancel keeps it where it was. Narrowing moves, renames and adds save directly.
  • 5Decisions applied, keys that move Verdict on 4: permissions stay independent (1B), Admin preset leaves secrets unticked (2B), folder admins create keys inside their folder (3). Folder picks follow the folder, single-key picks follow the key id through rename and move. Reveal still needs See. Who can...? gains a definitions-change simulator listing who gains and loses access.
  • 4One vocabulary, tickable permissions, glossary Verdict on 3: level words and Who can...? words disagreed; Admin was opaque; wants several permissions at once. Now every permission has one name used everywhere (See, Edit, Publish, Pin, Reveal, Reveal history, Define keys, Manage access, Manage machines, Manage deploys, Change settings, Manage projects), ticked independently; Viewer / Editor / Publisher / Admin are presets that only tick boxes. Permissions a narrow rule cannot carry are disabled with the reason. New Glossary page.
  • 3Three axes, folder-scoped Admin Verdict on 2: needs e.g. Admin on one folder in some environments. Where becomes projects › environments › keys, each "all, except" or "only", so db/ in staging + prod is three taps. Admin on a folder keeps publish, definitions and delegation inside the folder; the editor lists which project-wide powers (settings, machine access, adapters, pins) drop out and why.
  • 2Access as rules, with except One design instead of three layouts. Each member's access reads as lines: level (View / Edit / Publish / Admin, a display reading of the atoms), secret flags kept separate, where, and except. One include / except tree replaces the scope select, the key picker and the negative permission. An except narrows only its own rule; Who can...? shows when another rule still reaches.
  • 1aInline chips Members table unchanged; a limited grant carries a "stripe/ · 3/8 keys" badge. Grant dialog gains an Applies to step with a folder, group and key picker. Cheapest change; density grows with every limit. Verdict (1a to 1c): none clearer; negative permissions requested.
  • 1bOn the key Members stays scope-only. Definitions gains Key access: per folder, a capability by environment grid where each cell is "all holders" or an allowlist over current holders. Answers "only these people touch db/", cannot answer "Chen only touches stripe/".
  • 1cMember profile Members becomes a roster (seeded-from, reach, production-secret flag, limit count). Each member gets a page: access map of scope tree by capability, click a mark to limit it to keys, plus effective access per key. List size stays constant however detailed access gets.
