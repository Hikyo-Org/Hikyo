These workflows assume the instance is trusted, the user is logged in, and the
target resolves through flags, environment, a pin file, or a context.

## Inspect presence

```bash
hikyo values list --context production
hikyo values get DATABASE_PASSWORD --context production
```

An ordinary secret read returns metadata and presence, not plaintext. Use this
path for inventory and health checks.

## Stage and publish

`values set` stages a pending change and reports its version ID; delivery
continues to use the previous publication. Publish
the intended versions explicitly, after reviewing them:

```bash
hikyo values publish --context production --versions <version-id,version-id>
```

Publishing selected versions can also publish related pending versions required
by key-group closure. Review the complete set, including related drafts, before
running the command.

Publication needs `publish` separately from `edit`, validates the complete
resulting state and applies protection and change-approval policies.

`values import` and `values copy` are immediate bulk publications with their
own authorization and validation gates; they do not use this separate draft
publication step.

## Change approvals

A change-approval policy makes a publication wait for review. An administrator
with `project-settings` creates a policy for one environment (`--covers`) or,
when omitted, every environment in the project:

```bash
hikyo approval policy create --org example --project backend \
  --covers <env-id> --min-approvals 2 --ttl 86400 \
  --approver principal:<principal-id> --approver group:<group-id>:<binding-id> \
  --bypasser <principal-id>
hikyo approval policy list
hikyo approval policy update <policy-id> ...   # same flags as create; replaces the policy
hikyo approval policy delete <policy-id>
```

Defaults are `--min-approvals 1` and `--ttl 86400` (request expiry in seconds).
`--allow-self-approval` lets the requester count as an approver, `--disabled`
saves the policy without enforcing it, and `--approver` and `--bypasser` repeat.
An approver is a principal or a SCIM-mapped group binding. `update` replaces the
whole policy, so repeat every flag you want to keep.

With a policy in force, `values publish` of a covered environment stages a
review request instead of publishing, and prints the request. Anyone with read
on the environment can list requests. To approve or reject, you must be a
current approver on the policy and hold `publish` on the environment, and the
requester cannot approve their own request unless the policy sets
`--allow-self-approval`:

```bash
hikyo approval request list --env <env-id>
hikyo approval request approve <request-id> --env <env-id>
hikyo approval request reject <request-id> --env <env-id>
hikyo approval request merge <request-id> --env <env-id>
hikyo approval request bypass <request-id> --env <env-id> --reason "incident 4821"
```

An approval covers one exact change set. The requester merges it, through the
ordinary publish path, once enough approvals are in; nobody else can merge
another person's staged drafts. Editing the drafts, a new revision landing in
the environment, or changing the policy (including its approver list)
invalidates the request the next time anyone votes or merges. An approval stops
counting once its voter is no longer an eligible approver or loses `publish`; an
approved request that falls below quorum this way is invalidated at merge.
Requests expire after the policy's `--ttl`. The requester, if also a named bypasser on the policy, can merge their
own request without quorum with `bypass`. It needs `--reason` (at most 512
characters), is audited, and cannot change the policy.

Approve, reject and bypass each consume a reauthentication window bound to that
action and the request's keys. Merge consumes one only in a protected
environment, as any publish there does. A live window is reused; a protected
environment, or a window of `0s`, needs a new passkey ceremony for each
decision, in the browser or through the CLI's browser handoff. A covered environment refuses a
publish that spans several environments, so publish it alone. Value changes
that skip draft publication (`values copy`, `values import`, bulk apply and
cloning onto an existing environment) are also refused for a covered
environment, since they cannot be reviewed. The browser exposes the same flow under **Change
approvals** in the project. The server reports `hikyo_approval_requests_open`
and `hikyo_approval_requests_expired` on the operational listener.

## Set from a protected file

```bash
hikyo values set DATABASE_PASSWORD \
  --context production \
  --value-file /run/secrets/new-database-password
```

The value file is read locally. Keep its permissions narrow and remove it when
its owning secret-delivery mechanism does not manage its lifecycle.

## Set from the terminal

```bash
hikyo values set FEATURE_MODE --context production --stdin
```

Type the value, then end input. Do not put a value after a command-line flag.
Command arguments are visible through shell history and process inspection.

## Clear a value

```bash
hikyo values set OPTIONAL_ENDPOINT --context production --clear
```

Clear stages an `absent` draft. Saving it is allowed even for a required key;
publication refuses to leave that key absent. The published value remains
available until a valid publication changes it.

## Compare environments

```bash
hikyo values diff \
  --context production \
  --left development \
  --right production
```

The ordinary diff compares state without exposing secret plaintext. Add reveal
only when the comparison requires it and write the result to a protected file.

## Copy selected values

```bash
hikyo values copy \
  --context production \
  --from staging \
  --to production \
  --keys API_BASE_URL,FEATURE_MODE
```

Copy is explicit about source, destinations, and keys. It publishes immediately
after authorization and validation. Human copies into protected destinations
require the purpose-bound reauthentication ceremony; `--confirm-protected` does
not replace that ceremony. Machine copies require the explicit protected-target
confirmation in addition to their authorization.

## Reveal one secret

```bash
hikyo values get DATABASE_PASSWORD \
  --context production \
  --reveal \
  --output-file ./database-password
```

The output path must not already exist. Consume it, then remove it through your
normal secure-file procedure.

A disclosure needs a reauthentication window over the environment. When none is
live the CLI opens one: where the environment's effective window is above `0`
it prompts for an authenticator code at the terminal; where it is `0` (a
protected environment, or an instance that keeps the production default
`HIKYO_REAUTH_WINDOW_SECONDS=0`) a code cannot bind the decision, so the CLI
opens the browser to the same purpose-bound passkey ceremony the Values page
runs, naming exactly the secret keys the command will open, and continues once
you approve. Either way the session token rotates and is stored. `--dev`
instances default to a 15-minute window; raise an environment's window with
`hikyo project-settings set --env <env-id> --reauth-window-seconds 300`.

The browser reauthentication and workspace approval pages name the
organisation, project, environment and each key they cover, with the end of each
id beside the name. The change-approval page names the requester, the voters and
each key. Names are read through your own access, so one
you cannot read stays an id, and the approve button waits until the lookups
settle. Check that the named environment and keys are the ones you started.

## Import an existing `.env`

The schema is closed: `values import` refuses undeclared keys. To onboard a
`.env` you already have, first scaffold a declaration for every key, review it,
apply it, then import the values.

```bash
hikyo definitions scaffold --from .env > definitions-bundle.json
```

`scaffold` is offline. It contacts no server, reads only the file you give it,
and emits an additive bundle in which every key is `config` with a
`TODO: classify` marker. It cannot know which keys are secret, so it does not
guess. Open the bundle, change each secret key's classification, then apply it:

```bash
hikyo definitions plan --file definitions-bundle.json
hikyo definitions apply --plan <plan-id> --file definitions-bundle.json
```

With the keys declared, import the values through the same strict path:

```bash
hikyo values import --context production --from-dotenv .env
```

Any key still not declared is refused by name. That surfaced typo is the point.
After a successful import the source `.env` is still plaintext on disk; delete
it once the values have landed.

## Export as a dotenv file

```bash
hikyo values export --context production --format dotenv --reveal --output-file ./.env
```

`--format` selects `table`, `json`, or `dotenv`. The dotenv payload is escaped
exactly as the Compose renderer would deliver it. Without `--reveal` every
secret is omitted and their count is reported on stderr; with `--reveal` the
output carries plaintext and obeys the print triad (a new file, the terminal, or
explicit `--dangerously-print`).

For a development workstation or a coding agent, compare this with delivering
straight into the process in [Local development and coding agents](/docs/local-development/).
