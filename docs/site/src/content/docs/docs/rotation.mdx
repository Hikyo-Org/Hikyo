Scheduled rotation keeps one pair of secret keys (a PostgreSQL role name and
its password) fresh without a person pasting values: it mints a new role,
publishes it through an ordinary revision, waits for consumers to pick it up,
then drops the old role. PostgreSQL is the only provider, one adapter at a
time.

:::caution[A configured rotation runs]
Creating or resuming a rotation arms it: once its first run is due, the server
mints, publishes and later revokes credentials on its own, with no person
present. Read [How a run executes](#how-a-run-executes) before you create one.
Operator controls for an incident (pausing and deleting with run awareness, a
loud status for a held revoke) are still being completed, so deploy this release
together with its follow-up slice and watch `hikyo rotation show`, `hikyo rotation
list` (state and halt reason) and the audit log while rotations are enabled.
:::

## What a rotation records

- The [dynamic provider](/docs/dynamic-secrets/) that will mint the role. It
  must exist and have its admin credential set.
- The **password key** that will receive the credential. It must be
  secret-classified.
- The **username key** that will receive the generated role name. It is
  required: the password and the role name are delivered together, so a consumer
  always reads a matching pair.
- The **interval** between rotations: 1 hour to 90 days (`--interval`).
- The **revocation delay**, how long the superseded credential stays valid after
  the new one is published so consumers can pick it up: 5 minutes to 7 days, and
  always shorter than the interval (`--revocation-delay`).
- The **authority principal**: the person who created the rotation.

A bound that is hit is refused as `invalid`, naming the flag. The server renders the
value and the bound in the largest whole unit that divides them (`d`, then `h`, then
`m`), whatever unit you typed: `--interval 90m` is shown as `90m`, while `--interval
48h` is shown as `2d`, for example `--interval (interval_seconds) 30m is below the 1h
minimum rotation interval`. The record holds no password, no role name and no handle
for a minted credential.

## Who may configure it

Creating a rotation is a person's standing delegation, so the caller must be a
signed-in human who currently holds **edit**, **publish** and **reveal** on both
keys in the environment. A member access rule narrowed to specific keys applies:
both keys must be covered. Machine principals and developer credentials are
refused.

Because no per-publish ceremony will ever gate the unattended publishes that
follow, **creating and resuming a rotation each consume a publish
reauthentication ceremony** over the environment and both keys, the same step a
values publish of those keys takes. `hikyo rotation create` and `hikyo rotation
resume` prompt for it through the usual browser handoff.

The person who creates the rotation is recorded as the authority principal, and
the executor will re-check their authority in full before every step that can still
be rolled back; once a new credential is published, only fail-safe checks apply, so
losing authority can never strand a live old credential. It never acts as a system
principal. `resume` requires the caller to hold the same access on both keys, and
requires the recorded authority principal to still hold it (including through a rule
narrowed to those keys); if that authority was lost, `resume` refuses with a named
error rather than rescheduling, and the denial is recorded against the person who
asked, so a person who can only publish cannot re-arm someone else's delegation. A
person whose access to the keys comes only from key-narrowed rules can create a
rotation but cannot yet resume, pause or delete it; a person with the access
environment-wide can.

A rotation publishes unattended, so it is refused, by name, in an environment that
is **protected** (its publishes need a ceremony each time) or covered by an
**approval policy** (its publishes become approval requests). The same check runs
again at resume.

A key can be driven by one live rotation at a time, whichever role (password or
username) it plays. A key that belongs to a **key group** is refused: the
rotation would publish a value the group does not own. A key with a **pending
authority draft** (a staged change on either key) is also refused at create and
resume; clear or publish the draft first. Pause and delete need `publish` on the environment; list and
show need `read`.

## Providers, keys and environments

- Deleting a provider, or revoking its admin credential, **pauses** every active
  rotation that mints from it, and the audit event names the reason. `resume`
  refuses until the provider exists, is active and has its credential again.
- Marking an environment **protected**, or creating or enabling an approval policy
  that covers it (a project-wide policy covers every environment), **pauses** that
  environment's active rotations in the same step and records the person who did it
  and the reason (`environment_protected`, `approval_policy_enabled`). `resume` refuses
  until the environment is unattended again.
- `resume` also re-checks that both keys still exist and the password key is still
  secret-classified, and refuses by name if not.
- Deleting an environment is refused while a rotation in it is active, paused or
  halted, or while any of its runs may still hold a live role: a run in flight, a
  quarantined run, a revoke the provider refused, or a failed run that had already
  published. The refusal names the blocking rotation ids (up to ten of each kind).
  Delete each rotation first and let its runs finish; the history of deleted
  rotations is removed with the environment.

## How a run executes

Each cycle is a run with a durable phase, so a restart resumes or rolls back
cleanly:

1. `minting`: the server records the new role handle, then creates the role with
   a `VALID UNTIL` of the mint time plus a one-hour publish budget, the
   interval, the revocation delay and a 24 hour slack.
2. `minted` and publish: the new role is staged on both keys and published in one
   transaction as the recorded authority principal. Before it, the executor
   re-checks that authority and the environment in full (a gate).
3. `published`, then `overlap`: the superseded role stays valid for the
   revocation delay so consumers can pick up the new pair.
4. `revoking`, then `done`: the superseded role is dropped on the provider that
   minted it. Before it, the server confirms that neither key serves a value the
   revoke would break (for example after `revision restore`). If one does, the run
   is held in `revoke_refused` and nothing is dropped.

A failed step before the publish attempts to drop the new role and leaves the keys
unchanged. If that drop fails or its result is unknown, the run stays tracked
(`quarantine` or `failed` with the drop unconfirmed) and is retried until the
provider confirms the role gone, so the role can outlive the failure until then. A failure after the publish never fails the run: it keeps retrying
the drop with backoff and stays visible until it settles. A superseded role that
has already expired on its own (five minutes past its `VALID UNTIL`, to allow for
clock skew against the database) skips the restore check and settles by expiry
when the provider cannot be reached.

Failed runs retry with a bounded exponential backoff (5 minutes doubling to 6
hours, at most 12 attempts) inside a window that always leaves the superseded role
valid for the overlap. When the window or the attempt cap is spent, the rotation
moves to `halted` with a named reason: `retries_exhausted` (the schedule ran
out), `authority_lost` (the recorded person no longer holds the access) or
`gate_failed` (the environment became protected, a key changed, or a draft
appeared). A halted rotation shows its state and reason in `show` and `list`, is audited,
and does not extend the delivered credential; `resume` starts a new cycle. As the delivered credential nears its
expiry, the server extends its `VALID UNTIL` while the rotation is active and
the gate still holds.

If a publish succeeded but the keys later serve the old value again, the revoke
stays held (`revoke_refused`) until the old role expires on its own. A restore
never releases it. The server never drops a role that a key may be using.

Pausing a rotation does not touch a run in flight: a run that has published
continues to its end, and a run that has not published is rolled back by the next
gate check. The rollback attempts to delete the unpublished role; it is not proof
that the role is gone. A deletion that fails or whose result is unknown stays
tracked on the run and is retried, so during incident cleanup check that the run
has settled before treating the credential as removed.
Infrastructure faults (database or keyring) back off with the same capped
exponential schedule and do not spend the attempt cap; a rotation whose window has
closed is still halted. A decryption failure is a definite fault and counts as an
attempt.

## When the delivered credential expires

Pausing or deleting a rotation stops future rotations, but the credential it last
delivered keeps its expiry. `show` and `list` report it as `credential_expires_at`
(the `CREDENTIAL EXPIRES` column in the CLI), and `pause` and `delete` name it in
their response and on stderr, so stopping a rotation never silently schedules an
outage. A credential that was already in the keys before the first rotation ran is
the operator's own and is never revoked by a rotation.

## Create and manage

```sh
hikyo rotation create \
  --provider dprov_0198... \
  --key key_0198... --username-key key_0198... \
  --interval 30d --revocation-delay 1d \
  --env production

hikyo rotation list --env production
hikyo rotation list --env production --include-disabled
hikyo rotation list --env production --limit 50 --after rot_0198...
hikyo rotation show rot_0198... --env production
hikyo rotation pause rot_0198... --env production
hikyo rotation resume rot_0198... --env production
hikyo rotation delete rot_0198... --env production
```

`--interval` and `--revocation-delay` take Go durations (`90m`, `720h`) or a whole
number of days with a `d` suffix (`30d`). `list` shows live rotations; add
`--include-disabled` to include deleted history. A page holds up to `--limit`
rotations (1 to 500, default 100) in id order; when more follow, the CLI prints the
`--after` value that continues the list. `pause`, `resume` and `delete`
accept `--expected-generation N`, which fails
with a conflict if another change landed first. Resume schedules the next run one
interval from now, or sooner (down to now) when the delivered credential would
otherwise lapse first. Delete disables the rotation and keeps it as history; it
frees the keys for another rotation.

## API

The routes live under
`/api/v1/orgs/{org}/projects/{project}/environments/{environment}/rotations`:
`GET` (with the optional `include_disabled`, `limit` and `after` query parameters;
the response carries `next_after` while more follow) and `POST` on the
collection, `GET` and `DELETE` on
`/{rotation}`, and `POST` on `/{rotation}/pause` and `/{rotation}/resume`.
They require a human session. See the [HTTP API](/docs/http-api/).

## Audit

Every tracked provider effect (mint, publish, extend, revoke and the candidate
drop) is bracketed by an intent and an outcome event, a halt is
audited as `rotation.configured`, and an abandon writes one event per run it
closed (`rotation.quarantined` for a run that still owes a role, otherwise a
`rotation.run_outcome` of phase `abandon`). The executor's run events use the
rotation's authority and the run id as the correlation id, with origin `system`;
the abandon events are authored by the operator who deleted the rotation, with
the run id as the correlation id. `rotation.configured` records each create, pause, resume and delete with its
`action` and the environment, and a pause the system caused (provider deleted or
credential revoked, environment protected, approval policy enabled) with its
`reason`. Reads are not audited events. Audit payloads carry identifiers and
schedule values only, never a credential.

The events cover tracked effects only. When a worker loses its claim on a run
while the role is being created, it may issue a best-effort drop of that role
with no intent or outcome event, because it no longer holds the run's fence; the
worker that took the run drops the candidate under its own events. A missing event
is therefore not proof that no provider call was made. Conversely, an extend outcome with the error code `extend_skipped` records that
the extend ended before any provider call was made.
