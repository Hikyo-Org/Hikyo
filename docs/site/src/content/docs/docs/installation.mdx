Hikyo [1.0.0 is released](https://github.com/Hikyo-Org/Hikyo/releases/tag/v1.0.0).
Stable downloads include Linux, macOS and Windows archives, Linux packages,
notarized macOS DMGs, a container image and a Helm chart. Verify the complete
signed bundle before installation. Signed nightlies remain unsupported
prereleases; source builds are available for local evaluation and development.

## Stable downloads

Download the complete [v1.0.0 release bundle](https://github.com/Hikyo-Org/Hikyo/releases/tag/v1.0.0)
and follow [stable bundle verification](#verify-a-stable-bundle).
Use independently authenticated trust material and preserve the verifier's
cross-release state. Stop if public trust synchronization or verification is
incomplete; do not replace verification with a checksum from the same download.

| Distribution | 1.0.0 artifact |
| --- | --- |
| Linux, macOS and Windows | Archives for x86_64 and arm64, with the CLI and embedded browser UI |
| Linux packages | DEB, RPM, APK and Arch packages for amd64 and arm64 |

## Verify a stable bundle

Run this POSIX-shell procedure on Linux or macOS from a trusted Hikyo checkout.
It requires the Go version in `go.mod`, GitHub CLI (`gh`), and Cosign from the
pinned release toolchain in `.github/workflows/release.yml`. Windows users can
verify the complete bundle on one of these hosts before transferring the
matching verified Windows archive.

The checkout's `release/trust` must already be independently authenticated and
contain the current recovery-authorized stable policy and catalog. A checkout
whose trust synchronization is incomplete must stop here: `main` synchronizes
its trusted catalog to the 1.0.0 stable record only when the separate
trust-sync pull request merges, so verify from a checkout of `main` on or
after that merge; an earlier checkout fails this procedure even when the
bundle itself is authentic. Do not bootstrap trust from the downloaded
bundle. The [trust bootstrap guide](/release/signing/#one-time-trust-bootstrap)
explains the maintainer-owned authorization boundary.

```sh
(
  set -eu
  printf 'Persistent verification-state file outside the download directory: '
  IFS= read -r verification_state
  : "${verification_state:?Persistent verification-state file is required}"
  bundle=$(mktemp -d)
  printf 'Download directory: %s\n' "$bundle"
  gh release download v1.0.0 --repo Hikyo-Org/Hikyo --dir "$bundle"
  go run ./scripts/release/stable verify --trust release/trust \
    --state "$verification_state" --directory "$bundle" \
    --version 1.0.0 --commit 2ac7bb36633d3ae0a99d7724968ca8c3cbf18334 \
    --latest --published
  printf 'Verified stable bundle: %s\n' "$bundle"
)
```

Once a later stable release has superseded 1.0.0, the bundle remains
authentic but is no longer the signed latest release: historical verification
then replaces the `--latest` selection.

```sh
go run ./scripts/release/stable verify --trust release/trust \
  --state "$verification_state" --directory "$bundle" \
  --version 1.0.0 --commit 2ac7bb36633d3ae0a99d7724968ca8c3cbf18334 \
  --historical --published
```

The [per-release ceremony policy](/release/signing/#per-release-ceremony)
records that an older authorized release requires explicit historical
verification and cannot be presented as latest.

Success prints the authenticated `identity` with version `1.0.0` and
`published_oci_verified: true`, followed by the verified bundle directory.
Only then extract the matching platform archive or install a native package
below. Retain the state file across verifications for rollback and equivocation
protection. Keep the verified bundle for production admission; remove the
temporary download directory when it is no longer needed.

## Nightly container images

The nightly workflow publishes the same signed release binaries in a non-root
distroless image for `linux/amd64` and `linux/arm64`:

```sh
docker pull ghcr.io/hikyo-org/hikyo:nightly
docker run --rm ghcr.io/hikyo-org/hikyo:nightly --version
```

`:nightly` follows the newest successfully verified container publication.
Each image also has the corresponding GitHub prerelease version as a tag,
without the leading `v`. Find versions in [GitHub releases](https://github.com/Hikyo-Org/Hikyo/releases).
The container job can be retried independently if the GitHub release succeeded
but image publication failed.

For a repeatable deployment, pin the image digest reported by the nightly
workflow instead of the moving tag. Docker and Kubernetes use the same reference:

```yaml
image: ghcr.io/hikyo-org/hikyo@sha256:<verified-image-digest>
```

The image digest is signed with GitHub OIDC by the nightly workflow. See the
[nightly container verification runbook](https://github.com/Hikyo-Org/Hikyo/blob/main/docs/operations/signed-nightlies.md#container-images)
for the verification command and retry behavior. These signatures are separate
from the signed archive inventory. Pulling the image does not provision the
database, root key, or authenticated runtime bundle. Follow the
[manual deployment runbook](https://github.com/Hikyo-Org/Hikyo/blob/main/docs/operations/manual-upgrades.md)
for Compose and Helm inputs. The image has no shell.

## Native packages

Published releases include local-install packages for Linux amd64 and arm64:
Debian (`.deb`), RPM (`.rpm`), Alpine (`.apk`), and Arch Linux
(`.pkg.tar.zst`). Download the **complete** release bundle first and verify it
with a trusted verifier and recovery-authorized trust material.
Follow [stable bundle verification](#verify-a-stable-bundle) for
1.0.0, or the [signed-nightly runbook](https://github.com/Hikyo-Org/Hikyo/blob/main/docs/operations/signed-nightlies.md)
for a nightly. Do not install a package copied out of an unverified or draft bundle.

After verification, install the matching local file. These examples show amd64
names for version `1.0.0`:

```sh
sudo apt install ./hikyo_1.0.0_amd64.deb
sudo dnf install --nogpgcheck ./hikyo-1.0.0-1.x86_64.rpm
sudo apk add --allow-untrusted ./hikyo_1.0.0_x86_64.apk
sudo pacman -U ./hikyo-1.0.0-1-x86_64.pkg.tar.zst
```

`--nogpgcheck` and `--allow-untrusted` disable native repository signatures,
not Hikyo's verification. The preceding signed-bundle check is mandatory;
hosted Linux repositories and their package-index keys are intentionally not
published yet. For arm64, package filenames use `arm64` (Debian) or `aarch64`
(RPM, APK, and Arch).

Each package installs only `/usr/bin/hikyo` and
`/usr/share/doc/hikyo/LICENSE`. It does not create configuration, generate
keys, install a service, or start a server.

## macOS DMG and Homebrew

Hikyo is a command-line tool with an embedded browser UI. The DMG contains
`hikyo` and `LICENSE`, rather than an application to drag into Applications.
On [GitHub releases](https://github.com/Hikyo-Org/Hikyo/releases), choose the
release and download its `Darwin_arm64.dmg` for Apple Silicon or
`Darwin_x86_64.dmg` for Intel. Follow the
[stable DMG verification](#verify-a-stable-dmg) or
[nightly DMG verification](#verify-a-nightly-dmg) steps below, then open the image and copy
`hikyo` to a writable directory on your executable search path. Run
`hikyo --help` to check the installation.

Both images are Developer ID signed, notarized, and stapled before publication.
A nightly may omit both DMGs when Apple notarization or ticket stapling fails;
use an earlier release that includes the pair, or build from source. A missing
DMG is not a reason to disable Gatekeeper or remove quarantine.

Homebrew installs the executable from the same DMG. The nightly and stable
channels have separate casks and cannot be installed together:

```sh
# Signed development nightly, after its protected tap PR is merged:
brew install --cask hikyo-org/tap/hikyo@nightly
```

The stable `hikyo` cask has a separate protected tap PR. Once `Casks/hikyo.rb`
is published on the tap's `main` branch, install it with:

```sh
brew install --cask hikyo-org/tap/hikyo
```

The tap is [Hikyo-Org/homebrew-tap](https://github.com/Hikyo-Org/homebrew-tap).
If Homebrew cannot discover the tap, add its URL explicitly:

```sh
brew tap hikyo-org/tap https://github.com/Hikyo-Org/homebrew-tap
```

If Homebrew instead reports that the cask is unavailable, check that the
matching `Casks/hikyo@nightly.rb` or `Casks/hikyo.rb` exists in the tap's `main`
branch. Tapping alone cannot install a cask that has not been published.
Use the DMG download while the tap PR awaits review.

Homebrew does **not** verify Hikyo's pinned signing root. It authorizes the
tap/cask and verifies the DMG SHA-256 recorded in that cask; compromise of
the tap could replace the verification instructions, key, URL, and checksum
together. Use the complete signed-bundle verification flow above when the
Hikyo-root guarantee is required. The Homebrew path is convenient distribution,
not an official fail-closed installer.

### Verify a downloaded DMG

The following procedures verify the **complete release bundle**, including
both DMGs, before opening a download. Run them from the root of a trusted
Hikyo checkout with the Go version pinned in `go.mod` and the GitHub CLI (`gh`)
installed. See [Build from source](/docs/build-from-source/) for the toolchain.
The verifier runs from that trusted checkout, rather than from the download.

Use a current, independently authenticated `release/trust` directory containing
the pinned recovery root, public keys, signed metadata/catalog, and the selected
channel's authorized policy and Sigstore roots. Do not establish trust by
copying keys or policy from the same unverified download. If that public trust
material is missing or cannot be authenticated, stop before installation; the
[trust bootstrap runbook](/release/signing/#one-time-trust-bootstrap) describes
its maintainer-managed authorization.

Choose an exact **public** tag from [GitHub releases](https://github.com/Hikyo-Org/Hikyo/releases).
Each procedure prompts for that tag and downloads all its assets into a fresh
temporary directory. A failed download, signature, policy, revocation or hash
check stops the command before Finder opens. On success, the verifier prints
the authenticated release identity and Finder opens the verified directory.
Both architecture images must be present. Choose the image for your Mac and
continue with the copy-to-PATH instructions above.

### Verify a stable DMG

Enter the published stable tag `v1.0.0` and a path for a persistent verification
state file outside the download directory. Keep that state file across future
verifications to preserve remembered rollback and equivocation protection.

```sh
(
  set -eu
  printf 'Published stable tag: '
  IFS= read -r tag
  printf 'Persistent verification-state file: '
  IFS= read -r verification_state
  : "${verification_state:?Persistent verification-state file is required}"
  bundle=$(mktemp -d)
  gh release download "$tag" --repo Hikyo-Org/Hikyo --dir "$bundle"
  commit=$(gh api "repos/Hikyo-Org/Hikyo/commits/$tag" --jq .sha)
  go run ./scripts/release/stable verify --trust release/trust \
    --state "$verification_state" --directory "$bundle" \
    --version "${tag#v}" --commit "$commit" --latest
  test -f "$bundle/hikyo_${tag#v}_Darwin_arm64.dmg"
  test -f "$bundle/hikyo_${tag#v}_Darwin_x86_64.dmg"
  printf 'Verified DMGs: %s\n' "$bundle"
  open "$bundle"
)
```

The command requires the signed latest stable release. An authorized older
stable release needs explicit historical verification under the
[release verification policy](/release/signing/#per-release-ceremony).

### Verify a nightly DMG

Enter the exact nightly tag containing the images you selected. Nightlies
remain development prereleases. The verifier checks their authenticated
inventory against the separately recovery-authorized `nightly/v1` policy.

```sh
(
  set -eu
  printf 'Published nightly tag: '
  IFS= read -r tag
  bundle=$(mktemp -d)
  gh release download "$tag" --repo Hikyo-Org/Hikyo --dir "$bundle"
  go run ./scripts/release/nightly verify --trust release/trust \
    --directory "$bundle"
  test -f "$bundle/hikyo_${tag#v}_Darwin_arm64.dmg"
  test -f "$bundle/hikyo_${tag#v}_Darwin_x86_64.dmg"
  printf 'Verified DMGs: %s\n' "$bundle"
  open "$bundle"
)
```

An authenticated nightly may legitimately contain no DMGs after an Apple
service failure. In that case the presence checks stop installation. Select a
different published nightly that includes both images; do not substitute an
unlisted DMG or skip the bundle check.

## Unsigned development snapshots

Every successful trusted `main` build attaches a 14-day
`hikyo-development-<commit>` artifact to its
[GitHub Actions run](https://github.com/Hikyo-Org/Hikyo/actions/workflows/ci.yml?query=branch%3Amain).
It contains Linux, macOS, and Windows archives for `x86_64` and `arm64`, plus
checksums and an unsigned-development warning. GitHub may require a signed-in
account to download Actions artifacts.

Use a snapshot only for evaluation. Its commit is immutable and its checksums
detect download corruption, but it has no signed release manifest, official
installer, upgrade promise, or production support. The [online release ceremony](/release/online-signing/)
defines the path from built bytes to an official Hikyo release.

## Local evaluation

Use the source build with `hikyo server --dev`. Development mode creates its
SQLite database and root key in the working directory and listens only on
`127.0.0.1:8080`.

This path is intended for learning the product. It is not suitable for real
secret material or network exposure.

## Production preparation

A production-like deployment needs decisions that an installer cannot make for
you:

1. Choose SQLite or PostgreSQL.
2. Place the 32-byte root key outside the database backup.
3. Configure native TLS, or terminate HTTPS at a trusted reverse proxy with exact CIDRs.
4. Configure encrypted exports and run a restore drill.
5. Record the verified release version, source commit and artifact identities.

Production boot also requires the authenticated offline release bundle, the
separately pinned operator public key and durable installation state. The
installer places verified binaries; it does not supply instance-specific backup
proof or operator private custody. Follow the
[manual installation runbook](https://github.com/Hikyo-Org/Hikyo/blob/main/docs/operations/manual-upgrades.md)
for native, Compose and Helm inputs. Helm requires separate prepopulated public
artifact and writable installation-state PVCs. These are retained across pod
replacement and database recovery. The published bundle must pass verification
before production startup.

Hikyo fails closed when these boundaries are missing. Continue with the
[self-hosting baseline](/docs/self-hosting/) and
[server configuration](/docs/configuration/).

## Platform support

Stable 1.0.0 archives, unsigned development snapshots and signed nightlies cover
Linux, macOS, and Windows on `x86_64` and `arm64`. Source builds follow Go's
supported host platforms. The Unix-socket local evaluation flow is for Linux
and macOS; Windows CLI connections require HTTPS. Platform qualification limits
remain recorded in the release notes.

The server is designed to run as one binary. The browser UI is embedded when
the binary is built with the `ui` build tag.
