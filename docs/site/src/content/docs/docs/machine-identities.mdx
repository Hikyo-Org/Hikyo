Use a service account for a workload or automation job. Give it only the
capabilities and scope required by that workload.

Automation can create and delete ordinary environments, stage and publish its
own changes, and copy values under the existing disclosure gates. Environment
lifecycle requires project-wide `definitions-edit`; protected environments cannot
be deleted by machines. [The preview guide](/docs/preview-environments/) shows a
dedicated-project recipe with cloning, explicit publication, export and cleanup.

## Create and grant

```bash
hikyo sa create --name payments-deploy --kind workload
hikyo access grant add \
  --principal <mch_...> \
  --capability read \
  --env <environment-id>
```

Record the returned stable ID. List its grants before minting a credential.

In the browser, Machine access offers the same acts: *Create service account*,
*Add environment grant*, *Mint credential*, *Revoke*, and *Delete*
([Operate Hikyo from the browser](/docs/browser-operations/#the-lifecycle)).
Minting or rotating in the browser lets you choose the credential's lifetime
from presets; an estimated expiry is shown before you confirm, and a notice
after minting says when the instance policy ceiling shortened it.

`--principal` takes the service account's **principal** ID (`mch_...`, the
`principal_id` field of `hikyo sa list -o json`), not its `sa_...` row ID.

## Secret delivery: the machine-reveal opt-in

A workload or automation principal may hold `reveal` only under the project's
explicit machine-reveal opt-in. A workload may also hold `reveal-history`, but
only while an active pin routes that workload to a non-current revision. The
opt-in is off by default; while it is off every machine fetch delivers
configuration and secret presence only.

```bash
hikyo project-settings machine-reveal get
hikyo project-settings machine-reveal set --enabled true
hikyo access grant add --principal <mch_...> --capability reveal --env <env-id>
```

After pinning a workload to a non-current revision, grant its historical
delivery atom separately:

```bash
hikyo access grant add --principal <mch_...> --capability reveal-history --env <env-id>
```

The grant is refused without a live non-current pin. Releasing the pin leaves
the row visible for audit and reversal, but makes it inert and moves the
workload cursor. Automation principals cannot hold this atom because pins name
workloads.

Enabling needs `project-settings` and `reveal` at project scope and a
second factor; it admits a standing decryption capability onto machine
principals, which the command says before it writes. Withdrawing it
(`--enabled false`) makes every machine `reveal` and workload `reveal-history`
grant in the project inert on the next fetch and moves every machine cursor;
grant rows are untouched.

## Bearer credential

Mint to a new protected file:

```bash
hikyo sa credential mint \
  --sa <service-account-id> \
  --lifetime 720h \
  --output-file ./hikyo-token
```

The credential is shown once. A workload supplies it with `--token-file` or
`HIKYO_TOKEN`; Hikyo has no `--token` flag.

Prefer `--token-file`. Environment variables remain visible to the process and
may be copied by diagnostic tooling.

Rotate before expiry, distribute the new credential, verify it, then revoke the
old credential. A rotate command does not make distribution atomic.

Minting or rotating a credential for an account that can decrypt plaintext needs
a fresh reauthentication over each environment the account reaches, the same as
the Machine access page. The command asks for your authenticator code where the
environment's window allows one. Where it does not (window 0, a protected
environment, or no authenticator enrolled), it opens your browser to approve the
mint with a passkey, then continues. The approval covers that environment and no
keys. At a protected or 0-window environment it is one decision, used once;
otherwise the passkey opens the environment's reauthentication window for its
duration, as your authenticator code would. Without a browser the command refuses and names the
Machine access page.

## Credential policy

The instance policy limits lifetime, indefinite credentials, and the number of
live credentials per service account.

```bash
hikyo instance-config credential-policy get
hikyo sa credential list --sa <service-account-id>
```

`hikyo sa credential list` shows `expired` for credentials past their expiry.

Change policy only after checking existing workloads. Tightening a limit may
require staged rotation.

## OIDC federation

Federation removes stored bearer credentials. Configure a trusted issuer, then
create an immutable binding from exact claims to one service account.

Bindings do not accept wildcards or prefixes. Every platform binding must pin
its immutable identifiers:

- GitHub Actions: `repository_id`, `repository_owner_id`, `event_name`,
  `ref_protected`, `runner_environment`, and `job_workflow_ref`.
- Kubernetes: `/kubernetes.io/serviceaccount/uid`.

Every required pin is a JSON string, because the issuers emit them as strings:
GitHub sends `repository_id` as `"74"` and `ref_protected` as `"true"`. Pin them
as `name=value`, for example `--claim repository_id=74`. Pinning `repository_id=#74`
or `ref_protected=?true` is refused when the binding is created, because Hikyo
never folds a number or boolean onto a string and the binding could never match a
real token. Bindings that already exist are not re-checked.

Presence of the three newer GitHub pins is required, and you choose the value.
They narrow which workflow runs receive the credentials; they cannot stop a
compromised job from using credentials it was given.

- `ref_protected`: pin `true`. This refuses runs on branches that are not
  protected, such as a throwaway branch pushed by a stolen account. It does not
  stop an account that is allowed to bypass branch protection, or code that
  reaches the protected branch.
- `runner_environment`: pin `github-hosted`, unless you deliberately run
  self-hosted runners and pin `self-hosted`.
- `job_workflow_ref`: pin the workflow file and ref, for example
  `org/repo/.github/workflows/deploy.yml@refs/heads/main`. This refuses a new
  workflow file, but not a new job added to the same workflow file in the same
  repository. To close that, call a reusable workflow kept in a separate, locked
  repository and pin its ref. When the reusable workflow is called at a fixed
  commit, you can also pin `job_workflow_sha`; it is not required, because for a
  same-repository workflow it changes with every commit.

Copy the subject from a real token, for example with
[github/actions-oidc-debugger](https://github.com/github/actions-oidc-debugger),
instead of writing it by hand. GitHub repositories created, renamed or
transferred after 2026-07-15 use GitHub's immutable subject format, so do not
assume the `repo:owner/repository:ref:...` form.

Forgejo Actions bindings are refused because its tokens do not expose an
immutable repository identifier. Pinning `repository` and `event_name` cannot
prevent a renamed or reused repository path from inheriting authority. Use a
scoped bearer credential for Forgejo jobs instead.

Create a replacement binding for a change; do not edit the old binding in
place:

```bash
hikyo sa binding create \
  --sa <service-account-id> \
  --issuer <issuer-url> \
  --subject <subject> \
  --audience <audience> \
  --claim repository_id=<id> \
  --claim repository_owner_id=<id> \
  --claim event_name=push \
  --claim ref_protected=true \
  --claim runner_environment=github-hosted \
  --claim job_workflow_ref=<owner/repo/.github/workflows/file.yml@ref> \
  --replaces <old-credential-id>
```

The example pins the GitHub Actions set. A Kubernetes binding pins
`/kubernetes.io/serviceaccount/uid` instead.

GitHub bindings created in the web interface before this requirement pinned
`repository_id` and `repository_owner_id` as numbers and never matched a real
token. Recreate them as replacements.

The server revokes the predecessor and inserts the successor in one transaction.
There is no overlap window in which to verify both. Validate the new formula
before invoking replacement, then test the successor immediately afterward.

Each federation token presentation is verified before the caller is known, so
it counts against the per-source-IP allowance of 10 attempts per sliding
minute. CI jobs sharing one egress address share that allowance; see
[Rate limits](/docs/cli-reference/#rate-limits) for how to spread calls and
reuse one export per job.

## Keep production secrets out of CI

Federation narrows which runs receive a credential, but a compromised job can
still read whatever it was given. Keep production secrets out of CI: let
production workloads fetch at runtime, through the Kubernetes operator or
`hikyo run`, and give CI only deploy credentials.

Values the GitHub Actions deployment adapter writes to repository or
organization targets are readable by any workflow run that can reference
secrets, from any branch, for example through `toJSON(secrets)`. Prefer
environment targets protected by deployment-branch rules and, where your plan
offers them, required reviewers. GitHub Free, Pro and Team offer required reviewers only on public repositories;
deployment-branch rules also work on private repositories with Pro or Team.
Where neither is available, keep the value out of GitHub and let the workload
fetch it at runtime.
See [Deployment adapters](/docs/deployment-adapters/).

## Delete

```bash
hikyo sa credential revoke --sa <service-account-id> --id <credential-id>
hikyo sa delete --id <service-account-id>
```

Deletion is not a substitute for incident rotation. Revoke exposed credentials
immediately, then investigate their audit history.
