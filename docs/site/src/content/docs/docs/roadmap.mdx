with the self-hosted configuration and secrets service, controlled human
onboarding, workload delivery and recovery operations. Start with
[verified installation](/docs/installation/).

Registration remains closed unless an administrator creates an applicable policy.
Local email sign-up also needs configured mail delivery; provider sign-up needs
an enabled provider and its verified identity claims. A sign-up implementation
is not permission for uncontrolled registration. See
[Identity and access](/docs/identity-and-access/#human-onboarding).

## Remaining implementation boundaries

- External transit custody has a tested provider seam but no production HSM,
  KMIP or cloud-KMS provider. Software custody is the shipped implementation.
- Dynamic credential providers are a closed set containing PostgreSQL; they do
  not terminate already connected database sessions at lease expiry.
- Private PKI provides no ACME or OCSP service and no public trust.
- Bootstrap configuration rollouts support an enrolled singleton Kubernetes
  deployment. Multi-member HA bootstrap rollout, host/GitOps executors and
  cross-database migration are separate boundaries.

The narrower guides document additional limits. The browser parity manifest
(`api/parity.yaml`) tracks outstanding browser surfaces; it is not a promise
that every API operation already has a form.

## Post-release work and scope

The [execution tracker](https://github.com/Hikyo-Org/Hikyo/issues/527) owns
ongoing work. The [release checklist](https://github.com/Hikyo-Org/Hikyo/issues/79#issuecomment-6501530997)
and [published release notes](https://github.com/Hikyo-Org/Hikyo/releases/tag/v1.0.0)
retain acceptance closeout and known follow-ups. The earlier release plan and
September acceptance results remain dated evidence, not the current publication status.

Social sign-in and CLI browser/device login are implemented. Their accepted
post-1.0 scope disposition remains separate from implementation; #589 owns its
narrow text reconciliation. Kubernetes condition reporting is implemented and
#791 records real-cluster/browser acceptance at its tested source. Neither lane
should be presented as an unbuilt prerequisite solely because an older roadmap
placed it after 1.0.

Generic file destinations retain their accepted v1.1 release boundary.
Developer-credential project and policy administration and Transit browser
operations are implemented; see [browser operations](/docs/browser-operations/)
for the current browser boundary. Implementation before a release does not
automatically change an accepted release boundary.

## Release and deployment evidence

The 1.0 release notes retain real GitHub token contract acceptance (#1116),
explicitly skipped disposable GitLab CE qualification (#1119), public MCP client
profiles (#651), independent audit collection (#1037), live alerts (#1038),
installation-specific operations (#1055), external receipt reconciliation
(#1117), development-tool advisories (#1118) and container-local operator command
limitations (#1112). Clean-Mac, Intel native and Homebrew install/upgrade acceptance
also remain separate. Public verification and trust synchronization follow
publication. None is silently marked passed by announcing 1.0.

Each result remains bound to its tested source, artifact and environment.
A tag or published artifact alone does not establish deployment or runtime health.

Machine MCP defaults to five read-only tools, configuration plaintext and no
secret material. Explicit write opt-in adds staging and validation tools;
publication stays outside MCP. Named-client public-HTTPS and deployed multi-process proof
remain distinct from conformance fixtures. Human MCP identity and consent are a
separate product decision. See [MCP operations](/docs/mcp/).

Use the [implementation status](/implementation-status/) for the current
criterion-to-evidence inventory and the
[execution tracker](https://github.com/Hikyo-Org/Hikyo/issues/527) for owning
work. Issue labels and closed dependencies do not certify a release.
