Hikyo's current codebase includes the core configuration and secrets service,
controlled human onboarding, workload delivery and recovery operations. Features
that earlier roadmaps placed after 1.0 have since been implemented. This page
separates that implementation from release and deployment acceptance.

<Callout type="warn" title="Implementation snapshot, 9 October 2026">
  These docs track the repository implementation. Local tests and implemented
  surfaces do not certify a release, a deployed installation or a real identity
  provider. The [implementation status](/implementation-status/) records owning
  obligations; [release acceptance](https://github.com/Hikyo-Org/Hikyo/issues/79)
  needs exact-candidate evidence. This roadmap sets no release date.
</Callout>

Registration remains closed unless an administrator creates an applicable policy.
Local email sign-up also needs configured mail delivery; provider sign-up needs
an enabled provider and its verified identity claims. A sign-up implementation
is not permission for uncontrolled registration. See
[Identity and access](/docs/identity-and-access/#human-onboarding).

## Remaining implementation boundaries

- Transit browser forms remain tracked by
  [#820](https://github.com/Hikyo-Org/Hikyo/issues/820). Use the CLI or API today.
- External transit custody has a tested provider seam but no production HSM,
  KMIP or cloud-KMS provider. Software custody is the shipped implementation.
- Dynamic credential providers are a closed set containing PostgreSQL; they do
  not terminate already connected database sessions at lease expiry.
- Private PKI provides no ACME or OCSP service and no public trust.
- Bootstrap configuration rollouts support an enrolled singleton Kubernetes
  deployment. Multi-member HA bootstrap rollout, host/GitOps executors and
  cross-database migration are separate boundaries.

The narrower guides document additional limits. The browser parity manifest
(`api/parity.yaml`) tracks outstanding browser surfaces; it is not a promise
that every API operation already has a form.

## Release and deployment evidence

A final candidate must pass its required non-skipped SQLite/PostgreSQL,
compatibility, recovery, operator and browser evidence, together with the real
release-signing and trust-material checks. Earlier successful local runs do
not establish a different candidate's acceptance. A tag or published artifact
alone does not establish deployment or runtime health.

Machine MCP defaults to five read-only tools, configuration plaintext and no
secret material. Explicit write opt-in adds staging and validation tools;
publication stays outside MCP. Named-client public-HTTPS and deployed multi-process proof
remain distinct from conformance fixtures. Human MCP identity and consent are a
separate product decision. See [MCP operations](/docs/mcp/).

Use the [implementation status](/implementation-status/) for the current
criterion-to-evidence inventory and the
[execution tracker](https://github.com/Hikyo-Org/Hikyo/issues/527) for owning
work. Issue labels and closed dependencies do not certify a release.
