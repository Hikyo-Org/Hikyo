Hikyo migrations move forward only. A downgrade means restoring a pre-upgrade
archive with a compatible binary, not running a down migration.

## Release channels

`stable` follows signed production releases. `nightly` follows unsigned GitHub
prereleases built from the newest green, changed `main` commit. A stable
`1.0.0` makes the nightly line `1.1.0-nightly.<date>.<run>.g<sha>`; after stable
`1.1.0`, it advances to `1.2.0-nightly...`. Nightlies are evaluation artifacts,
not production releases.

Checks remain notification-only unless the instance operator configures the
separately privileged local updater helper. Remote apply admits stable releases
only; nightlies can never cross that boundary.

## Optional local updater helper

The Hikyo server never receives Docker, Git, cluster, host-root, or service
manager credentials. It can submit only a stable version and its fixed Hikyo
release URL over a Unix socket to `hikyo updater`. The helper then runs the same
bounded lifecycle for every supported backend:

`Plan → Backup → Verify → Apply → Health-check → Rollback`

1. Copy one strict profile from `install/updater/` to
   `/etc/hikyo/updater.json`; choose `flux`, `compose`, or `systemd`.
2. Install the shipped backend adapter and common verification library at the
   exact paths in the profile. Choose one of `hikyo-update-flux`,
   `hikyo-update-compose`, or `hikyo-update-systemd`. They receive version,
   release URL, and opaque job ID as separate arguments, never shell text.
3. Make the profile owner-only writable, create the dedicated identity, and
   install the example unit:

```bash
sudo groupadd --system hikyo
sudo useradd --system --gid hikyo --home-dir /var/lib/hikyo-updater \
  --shell /usr/sbin/nologin hikyo-updater
sudo install -d -o root -g hikyo -m 0750 /etc/hikyo
sudo install -o root -g hikyo -m 0640 install/updater/compose.json.example /etc/hikyo/updater.json
sudo install -o root -g hikyo -m 0640 install/updater/updater.env.example /etc/hikyo/updater.env
sudo install -o root -g root -m 0755 install/updater/hikyo-update-common /usr/local/libexec/hikyo-update-common
sudo install -o root -g root -m 0755 install/updater/hikyo-update-compose /usr/local/libexec/hikyo-update-compose
sudo install -m 0644 install/updater/hikyo-updater.service /etc/systemd/system/hikyo-updater.service
sudo systemctl daemon-reload
sudo systemctl enable --now hikyo-updater.service
```

For Flux or systemd, install the matching adapter instead of the Compose one.
Install `scripts/release/verify-bundle.sh` plus its `scripts/lib/release.sh`
dependency at the `HIKYO_VERIFY_BUNDLE_BIN` path, and copy the pinned release
trust root and keys to `HIKYO_TRUST_ROOT`'s directory.

If those identities already exist, verify their membership instead of
recreating them. The ordinary server identity needs membership of the `hikyo`
group only to open the mode-`0660` control socket. Add backend-specific writable
paths to a unit override; do not relax `ProtectSystem` globally. Fill only the
selected backend section in `/etc/hikyo/updater.env`; remove unused credentials.
Set `HIKYO_DB` to the running instance's datastore and
`HIKYO_BACKUP_RECIPIENTS` to its authorized age recipients so the backup phase
can create an encrypted export. Treat a PostgreSQL DSN in this file as a secret.
For Compose, `HIKYO_COMPOSE_ENV_FILE` must be a dedicated one-line image file
consumed as `${HIKYO_IMAGE}` by the Compose definition; the adapter replaces it
atomically and never writes unrelated application environment variables.

`HIKYO_ROLLBACK_BIN` is mandatory because restoring an encrypted database is
installation-specific and deliberately requires custody unavailable to the
generic adapter. It is an absolute, root-owned executable receiving three
separate arguments: the pre-update backup directory, version, and job ID. It
must stop access to the target, restore the archive into the deployment's empty
rollback target, and return only when that target is ready. The adapter restores
the previous binary/image/Git revision around that database action and then
requires the health check to pass.

4. Add `HIKYO_UPDATER_SOCKET=/run/hikyo-updater/updater.sock` to the ordinary Hikyo
   server service and restart it. Do not grant the server identity access to
   the phase executables' deployment credentials.
5. Sign in with `instance-config`. The WebUI reports the helper backend and
   offers remote apply only for the newest stable signed release. Submitting an
   update requires authentication from the last five minutes. Reconnecting
   preserves the remote browser session's original authentication time; if it
   is old, sign out and back in on the remote, then reconnect.

The profile is an adapter contract, not deployment folklore. A Flux phase
executable owns its narrowly scoped Git/cluster reconciliation, a Compose one
owns its rootless Docker/Compose project, and a systemd one owns only the named
binary and service actions. `backup` must create Hikyo's encrypted export with
the old binary. `verify` must fail closed against the pinned release trust root.
`rollback` must restore the backup-compatible artifact because migrations have
no down path.

Jobs are durable in `/var/lib/hikyo-updater/jobs.json`; only one can be active.
A helper restart marks an interrupted job failed instead of guessing that an
orphaned privileged command completed.

## Remote environments

Every connected workspace checks its remote directly. A remote admin sees that
environment's update toast and the persistent profile badge; ordinary members
receive no update metadata. Choosing “Update remote” sends the request straight
to the remote's authenticated API. The viewing Hikyo server never relays the
request and never holds fleet credentials.

## Before the change

1. Read the release notes and support status.
2. Record the running binary version and datastore engine.
3. Confirm the root key and backup identity are available through separate paths.
4. Run `hikyo backup export` and copy the archive off-host.
5. Verify recent restore-drill evidence.

Do not begin when you can create an archive but cannot prove which root key will
boot it.

## Automatic migration

`hikyo server` applies pending migrations by default. When backup recipients and
a destination are configured, it exports the old schema before changing it.

A configured export failure stops startup. An unconfigured policy records a loud
skip and continues, leaving no rollback archive.

## Controlled migration

For a maintenance window:

1. Stop the server.
2. Take and retain a manual export.
3. Install the new reviewed binary.
4. Run `hikyo migrate` with the production `HIKYO_DB`.
5. Start `hikyo server --auto-migrate=false` and check both probes.

With automatic migration disabled, the server refuses to serve when a migration
is pending or the database schema is newer than the binary.

## Verify the upgrade

```bash
curl --fail http://127.0.0.1:8080/healthz
curl --fail http://127.0.0.1:8080/readyz
hikyo doctor --instance hikyo.example.com
hikyo whoami --instance hikyo.example.com
```

Also verify one authorized metadata read and one representative workload. A
health response alone does not prove authentication, authorization, or delivery.

## Roll back

Stop the failed instance. Restore the pre-upgrade archive into an empty target
with a binary that supports its schema, then follow the full reconciliation
procedure.

Restoring invalidates all old authenticators. Include human recovery and machine
credential redistribution in the rollback time estimate.

See [backup and restore](/docs/backup-and-restore/) for the complete flow.
